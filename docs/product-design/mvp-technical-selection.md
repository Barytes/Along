# MVP 技术选型研究

更新日期：2026-10-02。本文整理本次会话中的产品要求、已确认决定和技术方案比较，作为 [PRD](./prd.md) 的补充。通信实现与部署方案仍待确认，尚未进行代码实现或运行验证。

## 产品目标与设计要求

产品帮助成员的 Agent 在工作过程中获取其他成员积累的资料、信息和经验。MVP 优先验证这些上下文是否能够帮助当前任务，采用尽量简单、便于尽快试用的实现。

成员应当能够管理个人数据、选择资料的存储方式，并自定义回答、关注留言、采集、整理和通信策略。功能模块通过明确接口协作，支持成员使用不同厂商的多个 Agent，避免将全部个人资料与执行集中到统一托管服务。

人的主要参与方式是审查上下文和浏览团队共享内容。成员需要在运行中和运行后查看自己的 Agent 获得了其他成员的哪些信息，以及这些信息与当前任务的关系；共享空间用于查看已经整理、对团队可复用的内容。人无需日常观看或参与 Agent 间通信。

## 已确认的决定

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| 群组可以读取通信内容 | 允许群组通信服务读取经过它的获准问题和回答 | 支持通信监督，例如检查提示词注入攻击；通信分析也有助于整理留言板和共享空间 |
| 定向记录实行角色权限 | 参与成员、管理员，以及群组授权的监督或整理 Agent 可以查看；其他普通成员不能查看 | 支持群组监督，同时区分定向交流与全组公开 |
| MVP 不接社交平台 | 先提供上下文审查和团队共享空间，Discord、Slack 接入留待后续 | 人的主要需求是判断上下文与任务的关系，以及浏览共享内容；第一版无需建设社交聊天入口 |
| 求助采用异步方式 | 不要求双方 Agent 同时在线，问题和回答可以等待后续处理或读取 | 不能期待团队成员的 Agent 一直在线 |

通信记录的查看权限与共享内容的发布权限需要分别处理。已确认允许监督和整理角色查看定向记录，但这不自动授权将全部定向回答发布给全组。

## 通信路线比较

通信服务负责接收、保存和提供问题与结果；个人响应器负责检索资料并回答。无论采用邮件还是 HTTPS，接收方电脑关机时，本地资料都无法被读取。异步机制保存的是待处理请求，回答需要等待接收方具备处理条件。

| 比较项 | 邮件服务与收发脚本 | HTTPS 请求服务与 SQLite |
| --- | --- | --- |
| 初始工作 | 复用邮件投递与离线保存；配置自动收发 | 开发小型 API，部署服务与持久磁盘 |
| 成员接入 | 每位成员配置邮箱及自动收发授权 | 每位成员配置群组服务地址及凭据 |
| 请求状态 | 脚本仍需保存请求 ID、处理状态与去重记录 | 直接在数据库中保存和查询 |
| 群组监督 | 统一经过群组专用邮箱时，仍需路由脚本；抄送不能强制保证完整记录 | 通过产品提交的通信由服务统一记录 |
| 定向查看与审查 | 需要协调邮箱访问权限，并将邮件转换为审查记录 | 应用按角色提供结构化查询 |
| 运维 | 邮件提供商维护邮箱，项目维护收发和路由脚本 | 项目维护一个应用、数据库文件和备份 |
| 适用起点 | 已有方便使用的邮件授权和收发代码 | 从零开始，准备让小组持续使用 |

邮件可以作为 Agent 的传输方式，不要求人通过邮件客户端参与。请求和回答使用唯一请求 ID 关联，正文携带获准内容、来源和有效期。为了满足群组监督，可使用管理员控制的群组专用邮箱与转发脚本，邮箱凭据不向全组开放。

邮件的简单程度取决于自动收发接入条件。例如 Gmail 支持 IMAP、SMTP 和 OAuth 2.0，仍需要配置授权并处理连接或凭据过期后的重连。[Gmail 自动收发文档](https://developers.google.com/workspace/gmail/imap/imap-smtp)

HTTPS 与 SQLite 也不是产品的必要前提。其优势是把成员权限、请求状态、通信记录与审查查询放在同一个小型应用中。SQLite 可以作为应用服务器的本地数据存储，无需独立数据库服务；成员的个人资料不因此需要迁入 SQLite。[SQLite 适用范围](https://www.sqlite.org/whentouse.html)

其他候选包括已有共享目录中的请求文件、NATS JetStream、RabbitMQ 和成员服务直接互联。共享目录适合已有访问条件的小型试验，但必须分别控制定向记录的权限；消息系统增加部署组件；直接互联增加服务地址、离线等待和监督记录的处理工作。上述路线均未选定。

## 当前 MVP 建议

当前建议采用一个持续在线的群组 HTTPS 服务与 SQLite，各成员在本机启动一个个人响应器，离线请求等待处理。第一版不配置个人云端 Agent。此方案尚未由用户确认。

| 组件 | 建议位置 | 主要责任 |
| --- | --- | --- |
| 群组通信服务 | 一台持续在线的服务器，初期由项目发起者维护 | 成员认证、保存请求和回答、处理状态、定向查看权限 |
| SQLite | 群组服务所在服务器的持久磁盘 | 保存获准通信、来源和共享内容 |
| 个人响应器 | 成员本机，由成员启动和停止 | 检索选定资料、执行分享规则与额度、调用所选模型并上传回答 |
| 工作 Agent 接入工具 | 工作 Agent 可访问的环境 | 发起求助、读取结果、保存任务关联，不控制工作 Agent 生命周期 |
| 查看界面 | 简单页面，完整个人任务背景保留在个人环境 | 上下文审查及团队共享内容阅读 |

建议先采用普通定时轮询，每位成员只运行一个响应器。请求使用唯一 ID 去重，异常显示状态并允许人工重试；长轮询、SSE、WebSocket 和多执行器调度不作为第一版前提。

本地响应器可以调用云端模型 API，但资料检索和权限检查仍在本机。为每位成员部署云端响应器，需要另外提供在线资料或同步授权副本，并处理更新、删除和凭据隔离。既然异步等待已经可接受，这些工作可以后续再讨论。

请求方取得请求 ID 后可以继续工作或结束会话。返回结果由通信服务保存，原会话仍可用时查询，否则在后续会话读取。第一版不承诺向已经结束的工作会话自动插入回答。

## 其他技术方向与待确认事项

以下方向均为候选建议。已有决定确定了产品行为和通信信任范围，尚未确定语言、框架、个人存储、模型或接入协议。

| 决策 | 当前候选方向 | 需要继续确定的内容 |
| --- | --- | --- |
| 通信与部署 | 群组 HTTPS 与 SQLite，个人响应器本地运行 | 是否采用；服务维护者、部署环境、请求有效期和记录保留时间 |
| 个人存储与检索 | 文件目录起步，必要时增加本地索引；连接器隔离资料源差异 | 首批资料来源、权限范围、删除与更新处理 |
| 多厂商接入 | MCP 提供求助工具，CLI 作为补充；自动接收请求单独适配 | 首批宿主、可访问环境及其能够提供的使用记录 |
| 回答执行 | 一个受限默认响应器，成员可选择模型或替换执行器 | 模型接入、可用工具、单次与累计额度 |
| 自定义策略 | 配置和提示词起步，外部进程接口作为高级扩展 | 各策略的输入输出与权限边界 |
| 成员间协议 | 小型版本化 JSON 协议，A2A 作为替代候选 | 消息字段、身份验证、重试及取消语义 |
| 语言与框架 | TypeScript 与 Node.js 是候选 | 根据首批接入能力确定，不预先引入完整 Agent 框架 |
| 共享空间 | 少量结构化内容或 Markdown 文件起步 | 存储位置、整理执行者、发布授权、版本与撤回规则 |

## 审查与验证

上下文审查应当展示当前任务的求助目的、提供成员、获得的具体内容、来源版本与时间，以及能够定位的后续采用情况。通信返回只能证明内容已提供；工作 Agent 的采用报告与实际输出或行动需要分别标明，缺少证据时显示采用情况未知。信息相关也不自动证明任务结果已经改善。

通信监督提供检查和处理依据，接收方个人服务仍需独立执行资料权限、工具限制和额度。通信分析不能代替这些执行限制，具体监督与处理机制尚待确定。

建议用一次离线求助验证部署方案：B 的响应器关闭时，A 提交问题并取得请求 ID；B 重新启动后在授权范围和额度内回答；A 随后读取结果并审查来源；普通成员 C 无法读取这次定向通信。只有符合分享规则的内容才能进入共享空间。

这项验证尚未执行。文档中的技术建议不代表已经实现、已经通过测试或已经证明产品有效。
