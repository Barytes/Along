# MVP 技术选型研究

更新日期：2026-10-04。本文整理本次会话中的产品要求、已确认决定和技术方案比较，作为 [PRD](./prd.md) 的补充。已确认产品默认托管在线响应器与授权资料副本，通过轻量桌面应用配置指定目录自动同步，求助与回答统一经过产品 HTTPS 服务，并由产品提供少量模型访问额度。成员已有的工作 Agent 是主要求助入口，首版采用远程 MCP 与 OAuth 浏览器登录授权、Skill 为可选使用指导，不提供 CLI；定向求助的在线回答消耗求助者的产品额度。具体部署技术仍待确认，尚未进行代码实现或运行验证。

## 产品目标与设计要求

产品帮助成员的 Agent 在工作过程中获取其他成员积累的资料、信息和经验。MVP 优先验证这些上下文是否能够帮助当前任务，采用尽量简单、便于尽快试用的实现。

成员应当能够管理个人数据、选择资料的存储方式，并自定义回答、关注留言、采集、整理和通信策略。功能模块通过明确接口协作，支持成员使用不同厂商的多个 Agent。MVP 由产品默认托管在线响应器与成员授权的资料副本，托管不要求成员迁入全部个人资料；成员继续控制资料范围、模型、回答策略与额度。

人的主要参与方式是审查上下文和浏览团队共享内容。成员需要在运行中和运行后查看自己的 Agent 获得了其他成员的哪些信息，以及这些信息与当前任务的关系；共享空间用于查看已经整理、对团队可复用的内容。人无需日常观看或参与 Agent 间通信。

当前按个人资料主要保存在本地进行设计，这是待真实用户观察验证的假设。MVP 要求在成员电脑关闭或原始资料系统暂时不可用时，仍能够依据已经授权并复制到在线环境的资料回答；尚未复制的本地更新无法在原始来源离线时取得。

## 已确认的决定

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| 群组可以读取通信内容 | 允许群组通信服务读取经过它的获准问题和回答 | 支持通信监督，例如检查提示词注入攻击；通信分析也有助于整理留言板和共享空间 |
| 定向记录实行角色权限 | 参与成员、管理员，以及群组授权的监督或整理 Agent 可以查看；其他普通成员不能查看 | 支持群组监督，同时区分定向交流与全组公开 |
| MVP 不接社交平台 | 先提供上下文审查和团队共享空间，Discord、Slack 接入留待后续 | 人的主要需求是判断上下文与任务的关系，以及浏览共享内容；第一版无需建设社交聊天入口 |
| 求助采用异步方式 | 不要求双方 Agent 同时在线，问题和回答可以等待后续处理或读取 | 不能期待团队成员的 Agent 一直在线 |
| 在线响应与授权资料副本 | 在线响应器依据授权资料副本处理请求，不以成员电脑或原始资料系统当时可用为前提 | 成员电脑关闭后也应能够回答；本地资料来源暂为待用户观察验证的假设 |
| 产品提供默认托管 | 产品默认托管在线响应器与授权资料副本；成员分别配置资料、模型、回答策略和额度 | 减少成员部署与维护在线环境的操作，同时保留成员配置与授权控制 |
| 指定目录自动同步 | 成员首次选择目录并设置筛选与分享规则；本地组件自动同步获准资料，后续符合规则的新增资料也自动同步并可用于向指定群组回答 | 接近个人 Agent 持续使用已有资料的体验，减少反复上传与维护操作 |
| 首版资料格式 | 首版支持 Markdown 和纯文本，其他文件类型后续增加 | 缩小首版资料处理范围 |
| 本地目录为权威来源 | 本地分享资料目录决定在线副本内容与范围；文件删除、移出目录或被排除后，跟随撤回在线使用 | 在线副本与本地分享范围保持一致，不作为独立维护的资料库 |
| 轻量桌面应用 | 通过本地界面完成目录与权限配置、同步状态查看及管理 | 减少成员安装后配置与日常管理的操作成本 |
| 首版桌面平台 | 首版同时支持 macOS 和 Windows | 支持两个平台的成员使用同一套目录同步与管理流程 |
| 离线副本继续可用 | 原始来源离线或暂时不可访问时，继续使用最近一次成功同步的副本，并展示来源版本与同步时间；收到删除或排除变更后撤回使用 | 保持成员电脑关闭后的回答能力，同时明确回答依据的时间 |
| 目录级分享授权 | 按目录设置可用于回答的群组，并支持排除文件或子目录；目录内其余符合规则的文件使用相同分享范围 | 授权范围容易理解，后续新增文件按同一规则自动处理 |
| 统一 HTTPS 服务 | 通过产品提交的求助请求与回答统一经过产品 HTTPS 服务 | 统一管理成员身份、定向权限、请求状态及通信监督 |
| 工作 Agent 产品无关 | 成员已有的工作 Agent 是主要求助入口；首版以产品托管的远程 MCP 服务器提供产品能力，Skill 为可选使用指导，不提供 CLI，不以特定产品名单限制产品能力 | 用户在原有工作流程内求助，减少另行安装调用工具和切换界面的操作 |
| 远程 MCP 身份认证 | 使用 OAuth 浏览器登录授权，成员添加服务地址后登录产品账户并授权工作 Agent 连接 | 减少手动复制和维护访问令牌的操作；按 MCP 标准 HTTP 授权机制接入 |
| 产品提供少量模型额度 | 产品提供少量模型访问额度，定向求助的在线回答消耗求助者额度；被求助者控制资料和响应方式，分配与耗尽处理待确认 | 别人的求助不减少分享者自己用于求助的产品额度；用户对自费分享意愿的担忧仍需实际试用观察 |

通信记录的查看权限与共享内容的发布权限需要分别处理。已确认允许监督和整理角色查看定向记录，但这不自动授权将全部定向回答发布给全组。

## 通信路线比较

通信服务负责接收、保存和提供问题与结果；个人响应器负责检索资料并回答。无论采用邮件还是 HTTPS，接收方电脑关机时，尚未复制的本地资料都无法被读取；在线响应器可以依据已经保存的授权资料副本回答。异步通信仍用于保存待处理请求与后续读取结果。

| 比较项 | 邮件服务与收发脚本 | HTTPS 请求服务与 SQLite |
| --- | --- | --- |
| 初始工作 | 复用邮件投递与离线保存；配置自动收发 | 开发小型 API，部署服务与持久磁盘 |
| 成员接入 | 每位成员配置邮箱及自动收发授权 | 每位成员配置群组服务地址及凭据 |
| 请求状态 | 脚本仍需保存请求 ID、处理状态与去重记录 | 直接在数据库中保存和查询 |
| 群组监督 | 统一经过群组专用邮箱时，仍需路由脚本；抄送不能强制保证完整记录 | 通过产品提交的通信由服务统一记录 |
| 定向查看与审查 | 需要协调邮箱访问权限，并将邮件转换为审查记录 | 应用按角色提供结构化查询 |
| 运维 | 邮件提供商维护邮箱，项目维护收发和路由脚本 | 项目维护一个应用、数据库文件和备份 |
| 适用起点 | 已有方便使用的邮件授权和收发代码 | 从零开始，准备让小组持续使用 |

邮件可以作为 Agent 的传输方式，不要求人通过邮件客户端参与。请求和回答使用唯一请求 ID 关联，正文携带获准内容、来源和有效期。为了满足群组监督，可使用管理员控制的群组专用邮箱与转发脚本，邮箱凭据不向全组开放。

邮件的简单程度取决于自动收发接入条件。例如 Gmail 支持 IMAP、SMTP 和 OAuth 2.0，仍需要配置授权并处理连接或凭据过期后的重连。[Gmail 自动收发文档](https://developers.google.com/workspace/gmail/imap/imap-smtp)

统一 HTTPS 服务已确认，SQLite 仍为存储候选。统一服务把成员权限、请求状态、通信记录与审查查询放在产品控制的应用中。SQLite 可以作为应用服务器的本地数据存储，无需独立数据库服务；成员的个人资料不因此需要迁入 SQLite。[SQLite 适用范围](https://www.sqlite.org/whentouse.html)

统一 HTTPS 服务以外的通信路线保留为比较，包括邮件、已有共享目录中的请求文件和成员服务直接互联。共享目录必须分别控制定向记录的权限，直接互联增加服务地址、离线等待和监督记录的处理工作。NATS JetStream、RabbitMQ 等消息系统也可以作为服务内部调度组件，但会增加部署组件，首版是否需要尚未确定。

## 当前 MVP 建议

已经确认由产品默认托管在线响应器与授权资料副本，通过同时支持 macOS 和 Windows 的轻量桌面应用配置指定目录自动同步，首版支持 Markdown 和纯文本。成员按目录设置分享群组，并排除文件或子目录。本地目录为权威来源，删除或移出获准范围后撤回在线使用；原始来源离线时，继续使用最近一次成功同步的副本。求助与回答统一经过产品 HTTPS 服务，产品提供少量模型访问额度。SQLite、具体同步实现及撤回的存储清理方式仍待确认。

| 组件 | 建议位置 | 主要责任 |
| --- | --- | --- |
| 群组通信服务 | 一台持续在线的服务器，初期由项目发起者维护 | 成员认证、保存请求和回答、处理状态、定向查看权限 |
| SQLite | 群组服务所在服务器的持久磁盘 | 保存获准通信、来源和共享内容 |
| 个人响应器 | 产品默认托管的在线环境 | 检索授权资料副本、执行分享规则与额度、调用所选模型并上传回答 |
| 授权资料副本 | 产品默认托管的在线存储 | 保存成员授权复制的资料及其来源版本，供个人响应器使用 |
| 本地同步组件 | 轻量桌面应用可访问成员指定目录的本地环境 | 按授权与筛选规则同步 Markdown 和纯文本的变更，并跟随本地删除或排除撤回在线使用 |
| 本地配置与状态界面 | macOS 与 Windows 轻量桌面应用 | 选择目录、按目录配置分享群组、排除文件或子目录、查看同步状态并管理资料来源；桌面框架待确认 |
| 远程 MCP 服务器 | 产品托管的在线环境，采用 OAuth 浏览器登录授权 | 向工作 Agent 提供发现成员、发起求助与读取结果等工具；同一业务服务执行权限与额度规则 |
| 可选 Skill | 支持 Skill 的工作 Agent 可读取的环境 | 说明何时求助、如何提供获准背景及使用回答，不承担业务权限执行 |
| 查看界面 | 简单页面，完整个人任务背景保留在个人环境 | 上下文审查及团队共享内容阅读 |

请求使用唯一 ID 去重，异常显示状态并允许人工重试。请求接收与调度方式根据在线环境确定；长轮询、SSE、WebSocket 和多执行器调度不作为第一版前提。

在线响应器的资料检索与权限检查需要在其在线环境执行，并处理资料更新、删除、授权撤回和凭据隔离。在线响应器不要求持续调用模型，也不要求每位成员拥有独立服务器；具体运行与隔离方式仍待选择。

请求方取得请求 ID 后可以继续工作或结束会话。返回结果由通信服务保存，原会话仍可用时查询，否则在后续会话读取。第一版不承诺向已经结束的工作会话自动插入回答。

## 部署组合与替代路线

通信方式、响应器部署和资料访问是三个独立选择。通信可以经过群组服务、直接连接成员或经过成员各自维护的服务；响应器可以运行在本机、成员控制的在线环境或产品统一托管环境；资料可以保留在本机、按请求读取在线来源，或同步为授权副本。群组监督和共享空间整理可以与这些组合分别搭配。

资料在线不等于响应器在线。本地响应器即使能够读取在线资料，也无法在本机关闭后执行回答；要在成员电脑关闭后回答，仍需一个能够运行并访问获准资料的在线执行环境。

| 方案 | 优势 | 代价及适用条件 |
| --- | --- | --- |
| 群组服务 + 本地响应器 + 本地或在线资料 | 无需另外部署个人在线执行环境；资料与策略由成员管理；群组统一保存异步请求 | 回答等待成员本机运行；在线资料接入仍需连接器和凭据管理。适合允许等待的首批试用 |
| 群组服务 + 成员在线响应器 + 在线原始资料 | 成员电脑关闭后仍可回答；无需专门同步一份完整资料副本；可保持成员执行环境独立 | 每次回答依赖来源可用性、授权和接口；需要管理在线运行环境、凭据、限流及检索缓存。适合首批资料本来就在在线系统中的群组 |
| 群组服务 + 在线响应器 + 授权资料副本 | 回答不依赖成员电脑或原始来源当时可用；可预先限定资料并建立稳定索引 | 必须维护更新、删除、授权撤回、衍生索引和版本；复制可能扩大资料暴露范围。适合资料相对稳定且愿意维护副本的成员 |
| 群组服务统一托管响应器及授权资料 | 成员接入操作少，部署和观察统一 | 产品承担成员凭据、资料隔离、执行额度和故障恢复；成员对执行环境的控制需要由接口与权限实现。适合以使用便利为首要目标的试用 |
| 点对点通信 + 成员响应器 + 群组监督与整理 | 成员直接交换资料，群组通信节点故障时仍可能直接交流 | 跨网络连接可能需要发现、打洞或中继；双方离线仍需队列或在线保存节点；监督依赖可靠上报。适合直接通信本身构成核心需求的情况 |
| 成员服务互联 + 群组监督与共享空间 | 成员独立管理服务、资料和执行；成员电脑关闭后可以由在线成员服务回答 | 需要维护多个服务、身份和权限配置，并协调消息去重、协议版本、重试及记录上报。适合已有个人服务的成员 |

点对点连接解决网络传输，不自动提供离线保存、群组权限或完整监督记录。libp2p 的连接机制包含 NAT 检测、打洞和中继，直接连接受限时可以使用中继。[libp2p 连接说明](https://docs.libp2p.io/connectivity/)

授权副本需要区分原始资料、索引、摘要和已发布回答。授权撤回应阻止后续使用并按规则清理副本及衍生数据；已经提供给其他成员的回答则按通信与共享内容的撤回规则处理。副本新鲜度需要在回答中展示来源版本和最后同步时间。例如 Google Drive 提供变更列表和分页令牌，连接器仍需把这些变更应用到自己的副本与索引。[Google Drive 变更接口](https://developers.google.com/workspace/drive/api/guides/manage-changes)

### 监督与自动整理

通信监督和共享空间整理是不同职责，可以在 MVP 中由同一个进程承担，但需要不同权限。监督读取获准通信并标记违规；整理提取可复用内容并维护来源、适用范围与版本。监督 Agent 能够读取定向记录，不自动获得向全组发布记录内容的权限。

自动发布可以依据成员预先授权的规则执行，无需要求成员逐条审批。范围不明确的内容先保存为参与方可见的整理草稿。整理后的摘要仍应保留原始依据；新回答与已有条目冲突时，应标记冲突，不能仅凭时间较新就覆盖已有结论。

在点对点方案中，上报通信与传递通信是两件事。请求 ID、双方回执、重试和待上报状态可以提高上报可靠性，但摘要上报不能支持检查完整原文，客户端故意绕过上报也不能由监督 Agent 单独发现。若要求每次通信在送达前受到检查，需要受控通信路径；若允许事后监督，则需要明确监督只覆盖实际上报的记录。

当前已确认由产品默认托管在线响应器与授权资料副本，采用指定目录自动同步；本地目录为权威来源，删除或移出获准范围后撤回在线使用。原始来源离线时，继续使用最近一次成功同步的副本。求助与回答统一经过产品 HTTPS 服务，具体同步实现及撤回的存储清理方式仍待确认。其他组合保留为方案比较。

### 资料接入与个人 Agent 体验

手动上传、指定目录自动同步和自动筛选资料属于不同的资料接入方式，不必改变产品帮助成员获取彼此资料与经验的核心定义，但会改变成员需要承担的日常操作及系统责任。手动上传要求成员维护一组资料；目录同步要求成员授权持续访问已有资料来源；自动筛选要求系统根据规则判断哪些工作内容适合纳入资料。

已确认采用指定目录自动同步。成员首次选择已有目录并设置筛选与分享规则，本地组件在运行且联网时自动同步获准资料变更；后续符合规则的新增资料也自动同步，并可用于向指定群组回答。在线响应器使用最近一次成功同步的副本回答，成员无需逐次上传或逐份重新授权。授权范围内的自动解析与检索索引为当前实现建议。

复制到个人在线副本与允许向其他成员回答是不同授权。首次配置应明确说明选定目录内符合规则的后续新增资料也会进入同步与回答范围；每次回答仍受成员配置的分享范围、回答策略和额度约束。成员可以选择已有目录或专门目录，无需为产品重新整理一套文件。资料副本的同步不自动授权将资料发布到群组共享空间。

首版按目录设置分享群组，并允许成员排除文件或子目录。目录内其余符合格式与筛选规则的资料使用相同分享范围，包括后续新增文件；首版不提供文件或子目录分别设置不同分享群组的功能。

自动处理可以先包括解析、索引和回答时检索。根据工作会话主动提炼经验、扩大采集来源或自动向全组发布内容，需要另外定义规则。减少使用摩擦的效果仍需观察用户实际配置、维护和审查过程。

首版仅同步和使用 Markdown 与纯文本。分享资料目录是内容与范围的权威来源，在线副本不独立接受内容修改；本地删除、移出获准目录或被筛选规则排除的文件，在线响应器应停止在后续回答中使用其副本。资料副本的撤回不自动撤回已经发出的回答或已发布的共享内容。

目录暂时无法访问、电脑关闭或扫描失败不等于文件删除。在线响应器继续使用最近一次成功同步的副本，回答中展示所用来源版本与同步时间，不因来源离线时间较长自动暂停使用。原始来源离线时，在线服务无法知道尚未同步的本地修改或删除；收到删除或排除变更后，停止在后续回答中使用相应资料。本地目录仍是权威来源，在线副本只反映已成功同步的目录状态。撤回生效的同步时机、索引失效处理及副本物理清理方式需要在具体实现设计中确定。

本地同步通过轻量桌面应用配置和管理，首版同时支持 macOS 与 Windows。分享规则采用目录级群组设置及文件或子目录排除。开机启动方式和桌面框架仍待确认。

### 工作 Agent 接入方式比较

接入目标是尽可能使用与 Agent 产品无关的接口，让具备相应调用能力的工作 Agent 发现成员、提交求助、读取回答。实际接入仍取决于宿主支持的协议、传输、认证和工具执行能力；接入某个协议不意味着可以控制工作 Agent 生命周期或读取其完整会话。

| 方式 | 定义与优势 | 代价及限制 | 当前建议 |
| --- | --- | --- | --- |
| MCP 服务器 | 按标准暴露工具、资源与提示模板；支持 MCP 的宿主可以发现和调用同一组求助工具 | 需要宿主支持相应传输与认证；工具可用不保证 Agent 主动求助、采用回答或提供采用证据 | 已确认的首版 Agent 入口 |
| HTTPS JSON API 与 OpenAPI 描述 | 独立于 Agent 产品的服务接口；OpenAPI 描述请求、响应与认证，便于自建 Agent、工具适配与集成 | Agent 宿主不一定允许直接 HTTP 调用或自动导入 OpenAPI；工具说明与安装仍需配套 | 独立公开接口留待实际需求决定 |
| CLI | 本地命令调用同一服务并返回结构化结果；允许执行命令的 Agent 可使用，也便于人工验证 | 需要安装与认证；云端或限制命令执行的宿主无法直接使用 | 首版不提供 |
| Agent Skill | 通过 SKILL.md、参考资料及可选脚本提供何时求助、怎样准备背景和怎样使用回答的流程说明 | Skill 自身不提供网络传输或权限执行，产品能力仍通过 MCP 调用 | 可选使用指导，不作为调用前提 |
| A2A | 标准化独立 Agent 服务的发现、交互、任务与结果交换，适合成员自托管响应器等互联需求 | 工作 Agent 宿主仍需具备 A2A 调用能力或适配；引入另一套协议与兼容验证工作 | 后续按独立服务互联需求增加 |
| 产品专用插件 | 可以使用特定宿主的界面、事件或上下文接口，提供更深的集成 | 每个产品需分别开发与维护，使用记录能力也由宿主决定 | 按实际需要增加 |

成员已有的工作 Agent 是主要求助入口，已确认由产品托管的远程 MCP 服务器提供产品能力，Skill 为可选使用指导，首版不提供 CLI。统一 HTTPS 产品服务承担业务状态、权限和额度，MCP 适配层可以与业务服务部署在同一应用内。服务内部可以复用发现成员、提交请求和读取结果等业务操作；是否独立公开 JSON API 与 OpenAPI 描述另行决定，不作为 MCP 接入的前提。[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)、[OpenAPI 规范](https://spec.openapis.org/oas/latest.html)、[Agent Skills 定义](https://agentskills.io/home)、[A2A 与 MCP 比较](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)

桌面应用与查看界面承担配置和审查职责。成员通过桌面应用选择分享目录、配置分享范围与响应方式，并查看同步状态；通过查看界面审查上下文和阅读共享内容。日常求助与使用回答发生在已有工作 Agent 中。被求助成员由其授权的托管在线响应器回答，工作 Agent 无需同时在线；让工作 Agent 直接接收和执行求助属于后续扩展。

已确认首版使用产品托管的远程 MCP，通过 HTTPS 上的 Streamable HTTP 提供工具调用。成员在工作 Agent 中配置服务地址，通过 OAuth 浏览器登录授权完成连接，无需安装本地 MCP 程序；本地 stdio 适配留待实际兼容需求决定。首版通过提交请求返回请求 ID、另一次调用查询状态与结果实现异步求助，不要求宿主支持额外的异步任务扩展。[MCP 架构与传输](https://modelcontextprotocol.io/docs/learn/architecture)

### 远程 MCP 身份认证

已确认采用 OAuth 浏览器登录授权作为远程 MCP 的默认认证方式。成员添加远程 MCP 地址后，由支持相应授权流程的宿主引导打开浏览器，登录产品账户并授权连接；服务根据获得的访问令牌识别成员。成员身份用于检查群组资格、定向记录权限和产品模型额度，工具参数中的成员标识不能替代认证身份。

实现遵循 MCP 的标准 HTTP 授权机制。OAuth 授权服务可以与产品服务部署在一起，也可以使用独立服务；具体提供商、产品账户登录方式、客户端兼容策略及令牌有效期另行选择。手动配置个人访问令牌不作为默认接入流程，是否提供此类兼容入口根据实际需求决定。[MCP 官方授权规范](https://modelcontextprotocol.io/specification/latest/basic/authorization)

### 产品模型额度与成员动机

已确认产品提供少量模型访问额度，降低成员为他人回答承担直接模型费用的参与成本。用户提出成员可能不愿意自费提供回答，因此额度设计应将提供方的分享意愿与费用分配分别考虑；这一动机判断需要通过实际试用观察，不作为已经验证的普遍行为结论。

产品模型额度的扣除归属与提供方授权的资源上限是两个独立规则。已确认 A 向 B 定向求助产生的在线回答模型消耗从 A 的产品额度扣除，B 继续设置分享范围、回答策略及单次和累计资源上限。这样别人的求助不消耗 B 自己用于求助的产品额度；A 的剩余额度不能提高 B 的授权上限。额度分配、失败与重试的扣除规则，以及留言板自主回答和共享空间整理的消耗归属仍待确认。当前建议请求方额度不足或提供方资源上限达到时，服务停止发起新的模型调用并说明原因，不自动改用成员自费账户；耗尽处理待用户确认。

## 审查与验证

上下文审查应当展示当前任务的求助目的、提供成员、获得的具体内容、来源版本与时间，以及能够定位的后续采用情况。通信返回只能证明内容已提供；工作 Agent 的采用报告与实际输出或行动需要分别标明，缺少证据时显示采用情况未知。信息相关也不自动证明任务结果已经改善。

通信监督提供检查和处理依据，接收方个人服务仍需独立执行资料权限、工具限制和额度。通信分析不能代替这些执行限制，具体监督与处理机制尚待确定。

建议用一次离线求助验证部署方案：B 先上传授权资料副本，再关闭电脑；A 提交问题，B 的在线响应器在授权范围和额度内依据副本回答；A 读取结果并审查来源版本及副本时间；普通成员 C 无法读取这次定向通信。只有符合分享规则的内容才能进入共享空间。

这项验证尚未执行。文档中的技术建议不代表已经实现、已经通过测试或已经证明产品有效。
