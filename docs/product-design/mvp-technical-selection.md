## 产品目标与设计要求

产品帮助成员的 Agent 在工作过程中获取其他成员积累的资料、信息和经验。MVP 优先验证这些上下文是否能够帮助当前任务，采用尽量简单、便于尽快试用的实现。

成员应当能够管理个人数据、选择资料的存储方式，并自定义回答、关注留言、采集、整理和通信策略。功能模块通过明确接口协作，支持成员使用不同厂商的多个 Agent。MVP 在群组自行部署的环境中统一运行在线响应器并保存成员授权的资料副本，在线响应不要求成员分别维护服务器；本地响应器由桌面应用运行，默认调用云端模型。成员继续控制资料范围、回答策略和响应资源上限，并可从管理员配置的可用模型列表选择自己的响应模型。

人的主要参与方式是审查上下文和浏览团队共享内容。成员需要在运行中和运行后查看自己的 Agent 获得了其他成员的哪些信息，以及这些信息与当前任务的关系；共享空间用于查看已经整理、对团队可复用的内容。人无需日常观看或参与 Agent 间通信。

当前按个人资料主要保存在本地进行设计，这是待真实用户观察验证的假设。本次已选择指定目录自动同步及在线响应，群组服务保存成员独立授权副本，普通成员通过问答取得获准回答与引用。资料处理涉及部署方与模型服务，具体保留及管理访问规则继续澄清。既有混合方案处理尚未复制的本地更新及仅保留在本地的资料，留待后续交付。

群组自行部署是项目的交付定位。项目提供可安装和维护的软件，部署方负责服务器、模型账户及日常运行；技术选择需要便于群组完成安装、配置、升级、备份与恢复。首版一次部署只服务一个群组，成员身份、管理员权限、通信记录与授权资料均在该部署范围内管理。不同部署之间是否互联，以及同一成员连接多个部署的使用方式，另行确定。

## 响应执行位置与资料可见范围

回答执行位置与原始资料公开范围是两个不同决定。本次选择群组服务保存成员独立授权资料副本并在线回答，先验证产品价值与 Agent 应用工程能力。下表保留与本地、混合方案的比较；具体资料处理与保留规则继续澄清。

| 方案 | 回答可用条件 | 原始资料可见范围与实现责任 |
| --- | --- | --- |
| 成员独立授权副本与在线响应 | 在线服务与模型可用，所需资料已成功同步；成员电脑关闭不影响已同步资料的查询 | 服务端按成员归属、授权及版本限定检索，求助者只取得获准回答与引用，不因求助获得原文列表或下载权限；服务端及模型仍处理回答所需资料 |
| 成员本机查询与响应 | 成员机器、资料与本地响应程序可用；离线时只能保存请求并等待 | 不需要将完整资料副本保存到群组服务；如果调用云端模型，必要片段仍提交模型处理 |
| 在线与本地混合 | 已同步资料在线回答，仅本地资料等待本地响应条件 | 同时实现两条路径、调度及累计额度，见既有混合设计；增加本次实现工作 |

服务器保存资料不等于将资料发布到共享空间。成员归属与检索授权由应用执行，普通群组成员的资料访问限制不等于部署管理员无法接触服务器资料。回答尽量及时不等于无生成延迟，具体时延需要完成检索、生成及分享检查后实测；没有运行中的资料访问端点且没有在线副本时，无法依据离线本机资料生成新的回答。

按成员隔离的全文检索可以沿用现有 SQLite 方向。SQLite FTS5 提供全文查询与排序，成员归属、授权状态和版本过滤仍由产品实现；无需仅为该隔离要求引入新数据库或独立成员服务器。此处是基于能力文档的实现判断，未做运行或检索质量验证。[SQLite FTS5](https://www.sqlite.org/fts5.html)

## 会话求助 Skill

用户主动调用求助 Skill 表达当前会话允许工作 Agent 自动求助；安装、被动读取或自动加载 Skill 不构成该授权。自动请求可以附带必要任务片段，问题及背景均遵守发起方分享范围，范围无法明确判断时取得发起方确认。会话结束、撤销及重新进入会话时的具体授权行为继续澄清。

Skill 提供流程指令，不替代服务器认证和业务权限。服务器继续验证认证连接中的成员身份、群组资格、目标成员授权及资源额度，不接受仅由模型填写的成员身份或 Skill 启用标志来扩大权限；会话授权如何记录及校验仍需设计。[Agent Skills 规范](https://agentskills.io/specification)、[MCP HTTP 授权](https://modelcontextprotocol.io/specification/latest/basic/authorization)

## MVP 实现就绪评估

当前设计足以开始实现本次 MVP。群组内定向求助、成员独立授权副本的在线响应、指定目录自动同步、工作 Agent 成员列表选择、主动调用 Skill 的会话自动求助授权，以及获准背景发送均已确定；资料撤回清理、按当前授权重新回答、定向记录按统一期限保留和候选回答批准或拒绝也已确定。2026-10-05 结束本轮设计访谈，剩余接口、状态、配置默认值及组件接入细节在实现规格与开发中完善，不再作为开始实现前必须由用户逐项回答的条件。当前设计就绪不等于已有可运行产品，也不等于完整实现规格已经完成。

剩余工作分为工程设计与集成验证。工程设计需要定义请求状态与执行领取、目录同步及索引失效、会话授权记录与背景分享检查、调用授权与额度预留结算、同步组件接口和配置参数。优先验证首个工作 Agent 宿主的成员列表选择、远程 MCP／OAuth 接入、LangChain 经模型服务的工具调用与用量返回，以及本地目录同步。输入 `@` 后出现群组成员列表是明确交付要求，其宿主接入机制尚未验证，不能仅凭远程 MCP 的业务接口认定该界面交互已经实现。本地格式转换和混合响应属于后续能力，不作为本次 MVP 的实施前置条件。

本次验收需要覆盖：B 指定目录中的获准资料及其变化按规则同步；B 关闭电脑后，A 在工作 Agent 中输入 `@`、选择 B 并依据已同步资料获得带来源的在线回答；用户主动调用 Skill 后，工作 Agent 在当前会话内按授权自动求助并仅发送获准背景；分享检查与成员确认决定回答提供，撤回来源阻止仍依赖该来源的待发回答；普通成员 C 不能读取 A 与 B 的定向记录。再由实际求助任务验证所得资料是否有帮助。

本节是设计就绪判断。仓库尚未有应用实现，未执行上述接入、转换、权限或用量验证。

## 已确认的决定

| 决定 | 内容 | 理由 |
| --- | --- | --- |
| 群组可以读取通信内容 | 允许群组通信服务读取经过它的获准问题和回答 | 支持通信监督，例如检查提示词注入攻击；通信分析也有助于整理留言板和共享空间 |
| 定向记录实行角色权限 | 参与成员、管理员，以及群组授权的监督或整理 Agent 可以查看；其他普通成员不能查看 | 支持群组监督，同时区分定向交流与全组公开 |
| MVP 不接社交平台 | 首次交付提供基础上下文审查，团队共享能力按后续交付推进，Discord、Slack 接入留待后续 | 日常求助通过已有工作 Agent 完成，第一版无需建设社交聊天入口 |
| 求助采用异步方式 | 不要求双方 Agent 同时在线，问题和回答可以等待后续处理或读取 | 不能期待团队成员的 Agent 一直在线 |
| 本次 MVP 范围 | 成员独立授权资料副本的在线响应与指定目录自动同步；工作 Agent 输入 `@` 后显示群组成员列表并形成明确成员引用；主动调用 Skill 授予当前会话自动求助权限，允许发送符合分享规则的必要背景 | 优先验证产品价值与 Agent 应用工程能力，本地响应与混合调度后续交付 |
| 业务与响应核心语言 | TypeScript／Node.js 实现群组业务服务与在线、本地响应核心；Python 用于本地文件转换工具 | 复用响应流程及协议代码，转换能力通过独立工具提供 |
| 响应核心框架 | LangChain JavaScript 的 createAgent，在线与本地复用响应核心 | 满足多轮工具调用，并积累成员希望用于求职的框架实践经验 |
| 首版执行恢复 | 未完成查询允许重新执行，已生成候选回答和待确认状态可靠保存 | 首版没有必须从中途检查点恢复的要求；重试继续遵守权限与剩余额度 |
| Token 计量与额度周期 | 同一次求助累计模型服务报告的实际总 Token，不同模型按 Token 数量计量，缓存与推理明细不重复累计；成员额度按月分配，管理员可以调整和补充 | 查询、回答、分享检查和重试归属同一次求助；初始额度及单次上限作为管理员配置项 |
| 等待期限配置 | 求助者为自己发出的请求配置默认等待时间，可按次调整；提交时保存明确截止时间 | 请求有效期对应求助者任务需要，被求助者继续控制响应授权与资源上限 |
| 撤回与待发回答 | 服务收到资料删除、排除或授权撤回后，阻止仍依赖该资料的候选回答提供，先停止使用再清理正文副本、索引及摘要；默认在同次请求的剩余额度及期限内按当前获准资料重新生成 | 待发回答遵守当前授权；已提供定向记录按群组统一期限保留，到期清理正文与引用，见 ADR-0011 |
| 群组业务存储 | SQLite 保存成员、请求状态、回答、额度记录和资料元信息；授权资料正文副本保存在服务器持久文件目录 | 减少首版独立数据库服务，状态与资料正文共同备份恢复 |
| 成员登录 | 管理员邀请成员，成员设置本部署账户密码，浏览器登录后授权工作 Agent 连接远程 MCP；管理员负责账户恢复 | 首版不依赖外部身份服务，具体认证组件继续选择 |
| 本地资料来源 | 成员指定、未同步的本地查询目录；首版处理 Markdown、PDF、Word、Excel、PowerPoint 的可提取文字与表格，暂不支持图像理解 | 按首批资料选择工具，不要求成员重新整理目录 |
| 本地工具能力 | 提供多轮 Agent 工具调用，产品提供目录列出、搜索、读取和文件解析工具；首版不开放任意 Shell、Python 或成员自行添加的第三方工具 | 让 Agent 按问题查询已有资料，工具执行受目录授权与资源上限约束 |
| 本地配置体验 | 成员指定目录与分享规则，可通过分享偏好或分享 Skill 表达；不要求分别维护两份资料范围清单 | 减少配置操作，按允许、禁止及待确认结果提供回答，配置时说明必要片段经过模型服务处理 |
| 自动回答分享规则 | 符合允许规则自动发送；命中禁止规则则删减或拒绝提供；规则未覆盖或无法判断时由成员确认；禁止规则优先于允许规则 | 按预先授权自动回答，范围不明确时取得成员确认 |
| 在线与本地混合响应 | 在线响应器使用授权资料副本；本地响应器按成员授权访问未同步的本地资料；两条路径均遵守资料分享范围与资源限制 | 支持及时在线回答，同时不要求成员把全部资料复制到群组服务 |
| 本地响应器宿主 | 由桌面应用运行本地响应器，不依赖成员已有工作 Agent 会话 | 统一管理本地请求接收、资料权限与执行状态 |
| 本地回答能力 | 桌面应用访问成员获准本地资料，默认调用云端模型理解资料并生成回答 | 支持从隐私与经验混合的资料中提炼可分享内容，最终回答遵守成员分享规则 |
| 响应路径选择 | 成员预设本地查询范围，符合规则的请求交给本地响应器；其余优先使用在线副本，依据不足时可以请求本地补充；需要本地查询而本地不可用时保留待处理状态 | 让必须查询本地来源的问题按规则处理，区分副本缺少记录与原始来源没有记录 |
| 默认模型执行方式 | 在线响应器和本地响应器默认使用云端模型；成员从管理员配置的可用模型列表选择响应模型 | 共用群组模型配置与 Token 额度规则 |
| 在线响应与授权资料副本 | 在线响应器依据授权资料副本处理请求，不以成员电脑或原始资料系统当时可用为前提 | 成员电脑关闭后也应能够回答；本地资料来源暂为待用户观察验证的假设 |
| 群组自行部署 | 团队或群组自行部署并管理服务；在线响应器与授权资料副本在群组部署环境中统一运行 | 让有需要的群组自行安装和使用，成员无需分别维护在线响应服务 |
| 首版部署范围 | 一次部署只服务一个群组，各群组分别部署 | 简化成员身份、管理员权限、模型账户及资料范围的管理 |
| 指定目录自动同步 | 成员首次选择目录并设置筛选与分享规则；本地组件自动同步获准资料，后续符合规则的新增资料也自动同步并可用于向指定群组回答 | 接近个人 Agent 持续使用已有资料的体验，减少反复上传与维护操作 |
| 首版同步资料格式 | 首版同步副本支持 Markdown 和纯文本，本地另支持 PDF 与 Office 的文字及表格转换查询 | 缩小首版资料处理范围 |
| 本地目录为权威来源 | 本地分享资料目录决定在线副本内容与范围；文件删除、移出目录或被排除后，跟随撤回在线使用 | 在线副本与本地分享范围保持一致，不作为独立维护的资料库 |
| 轻量桌面应用 | 通过本地界面完成目录与权限配置、同步状态查看及管理 | 减少成员安装后配置与日常管理的操作成本 |
| 桌面框架 | Electron，承载 TypeScript 本地响应核心与内置 Python 转换工具 | 复用 Node.js 响应逻辑和跨平台桌面界面 |
| 首版桌面平台 | 首版同时支持 macOS 和 Windows | 支持两个平台的成员使用同一套目录同步与管理流程 |
| 离线副本继续可用 | 原始来源离线或暂时不可访问时，继续使用最近一次成功同步的副本，并展示来源版本与同步时间；收到删除或排除变更后撤回使用 | 保持成员电脑关闭后的回答能力，同时明确回答依据的时间 |
| 目录级分享授权 | 按目录设置可用于回答的群组，并支持排除文件或子目录；目录内其余符合规则的文件使用相同分享范围 | 授权范围容易理解，后续新增文件按同一规则自动处理 |
| 统一 HTTPS 服务 | 通过产品提交的求助请求与回答统一经过群组 HTTPS 服务 | 统一管理成员身份、定向权限、请求状态及通信监督 |
| 工作 Agent 产品无关 | 成员已有的工作 Agent 是主要求助入口；首版以群组部署的远程 MCP 服务器提供产品能力，Skill 为可选使用指导，不提供 CLI，不以特定产品名单限制产品能力 | 用户在原有工作流程内求助，减少另行安装调用工具和切换界面的操作 |
| 远程 MCP 身份认证 | 使用 OAuth 浏览器登录授权，成员添加服务地址后登录该部署中的成员账户并授权工作 Agent 连接 | 减少手动复制和维护访问令牌的操作；按 MCP 标准 HTTP 授权机制接入 |
| 定向求助额度归属 | 定向回答消耗求助者额度，被求助者控制资料、回答策略和响应资源上限；模型账户由管理员配置，成员额度按月分配并可调整、补充 | 分别管理求助消耗和提供方授权，避免把队友的求助消耗记到资料提供方 |
| 首版在线响应器执行范围 | 只提供授权资料检索与模型回答，不开放通用代码执行、联网搜索或第三方工具；本地采用产品提供的资料查询工具 | 优先验证已有资料对队友任务的帮助 |
| 回答模型配置 | 管理员配置可用模型列表、服务地址、API Key 和群组默认模型；成员可为自己的响应器选择列表中的模型，未设置时使用默认模型；成员不自行提交 API Key | 保留成员模型偏好，同时由群组统一管理模型账户与可用范围 |
| 求助额度计量 | 全组消耗上限与成员求助额度按 Token 用量计量 | 累计模型服务报告的总 Token，缓存与推理明细不重复累计 |
| 群组与成员额度限制 | 提供全组消耗上限和每位成员的求助额度，默认启用；管理员可以调整或关闭；关闭后仍记录消耗；提供方响应资源上限独立生效 | 支持群组控制消耗，也允许自行承担费用的小组按需放宽限制 |
| 提交时检查求助额度 | 需要消耗求助额度的定向求助在提交时检查求助者额度；不足则返回明确原因，由管理员补充额度后重新提交；关闭成员额度限制时仍记录消耗 | 不让额度不足的请求进入等待回答的状态 |

通信记录的查看权限与共享内容的发布权限需要分别处理。已确认允许监督和整理角色查看定向记录，但这不自动授权将全部定向回答发布给全组。

已确认共用在线响应服务，每位成员保留独立响应配置，每次请求拥有独立执行上下文。已确认采用独立模型服务，供在线响应器与桌面应用共同调用；首版调用限于产品内求助响应。具体调用授权与额度执行方式继续确定。

## 通信路线比较

通信服务负责接收、保存和提供问题与结果；个人响应器负责检索资料并回答。无论采用邮件还是 HTTPS，接收方电脑关机时，尚未复制的本地资料都无法被读取；在线响应器可以依据已经保存的授权资料副本回答。异步通信仍用于保存待处理请求与后续读取结果。

| 比较项 | 邮件服务与收发脚本 | HTTPS 请求服务与 SQLite |
| --- | --- | --- |
| 初始工作 | 复用邮件投递与离线保存；配置自动收发 | 开发小型 API，部署服务与持久磁盘 |
| 成员接入 | 每位成员配置邮箱及自动收发授权 | 每位成员配置群组服务地址及凭据 |
| 请求状态 | 脚本仍需保存请求 ID、处理状态与去重记录 | 直接在数据库中保存和查询 |
| 群组监督 | 统一经过群组专用邮箱时，仍需路由脚本；抄送不能强制保证完整记录 | 通过产品提交的通信由服务统一记录 |
| 定向查看与审查 | 需要协调邮箱访问权限，并将邮件转换为审查记录 | 应用按角色提供结构化查询 |
| 运维 | 邮件提供商维护邮箱，项目维护收发和路由脚本 | 部署方维护一个应用、数据库文件和备份 |
| 适用起点 | 已有方便使用的邮件授权和收发代码 | 从零开始，准备让小组持续使用 |

邮件可以作为 Agent 的传输方式，不要求人通过邮件客户端参与。请求和回答使用唯一请求 ID 关联，正文携带获准内容、来源和有效期。为了满足群组监督，可使用管理员控制的群组专用邮箱与转发脚本，邮箱凭据不向全组开放。

邮件的简单程度取决于自动收发接入条件。例如 Gmail 支持 IMAP、SMTP 和 OAuth 2.0，仍需要配置授权并处理连接或凭据过期后的重连。[Gmail 自动收发文档](https://developers.google.com/workspace/gmail/imap/imap-smtp)

统一 HTTPS 服务与 SQLite 业务存储已确认。统一服务把成员权限、请求状态、通信记录与审查查询放在群组管理的应用中。SQLite 保存业务状态与资料元信息，授权资料正文副本保存在服务器持久文件目录，两者共同备份恢复。模型网关的内部存储要求另行核对。[SQLite 适用范围](https://www.sqlite.org/whentouse.html)

统一 HTTPS 服务以外的通信路线保留为比较，包括邮件、已有共享目录中的请求文件和成员服务直接互联。共享目录必须分别控制定向记录的权限，直接互联增加服务地址、离线等待和监督记录的处理工作。NATS JetStream、RabbitMQ 等消息系统也可以作为服务内部调度组件，但会增加部署组件，首版是否需要尚未确定。

## 既有完整方案与组件职责

本节描述既有完整方案。本次采用指定目录同步及在线响应，本地响应与混合调度后续交付，成员引用的宿主接入仍待验证，同步组件与界面交付形式继续澄清。

已经确认采用在线与本地混合响应：群组环境运行在线响应器并保存授权资料副本，本地响应器访问成员仅保留在本地的获准资料。通过同时支持 macOS 和 Windows 的轻量桌面应用配置指定目录自动同步，首版支持 Markdown 和纯文本。成员按目录授权向所连接部署的群组分享，并排除文件或子目录。本地目录为权威来源，删除或移出获准范围后撤回在线使用；原始来源离线时，继续使用最近一次成功同步的副本。求助与回答统一经过群组 HTTPS 服务，模型账户由管理员管理，成员可选管理员允许的模型；额度累计实际总 Token，成员按月分配额度，管理员可以调整和补充。SQLite 加持久文件目录已确认，具体同步实现、清理时限及备份清理规则仍待确认。

| 组件 | 建议位置 | 主要责任 |
| --- | --- | --- |
| 群组通信服务 | 群组选择并维护的持续在线环境 | 成员认证、保存请求和回答、处理状态、定向查看权限 |
| SQLite | 群组服务所在服务器的持久磁盘 | 保存获准通信、来源和共享内容 |
| 个人响应器 | 群组自行部署的在线环境 | 检索授权资料副本、执行分享规则与额度、调用所选模型并上传回答 |
| 授权资料副本 | 群组自行部署的在线存储 | 保存成员授权复制的资料及其来源版本，供个人响应器使用 |
| 本地响应器 | 成员的 macOS 或 Windows 桌面应用 | 按成员预设范围接收请求，访问获准本地资料，调用云端模型按回答策略生成答案并提交；经独立模型服务调用，授权范围外回答由成员确认，具体工具与调用授权待确认 |
| 本地同步组件 | 轻量桌面应用可访问成员指定目录的本地环境 | 按授权与筛选规则同步 Markdown 和纯文本的变更，并跟随本地删除或排除撤回在线使用 |
| 本地配置与状态界面 | macOS 与 Windows 轻量桌面应用 | 选择目录、按目录配置向该部署群组分享的授权、排除文件或子目录、查看同步状态并管理资料来源；桌面采用 Electron |
| 远程 MCP 服务器 | 群组部署的在线环境，采用 OAuth 浏览器登录授权 | 向工作 Agent 提供发现成员、发起求助与读取结果等工具；同一业务服务执行权限与额度规则 |
| 可选 Skill | 支持 Skill 的工作 Agent 可读取的环境 | 说明何时求助、如何提供获准背景及使用回答，不承担业务权限执行 |
| 查看界面 | 简单页面，完整个人任务背景保留在个人环境 | 上下文审查及团队共享内容阅读 |

请求使用唯一 ID 去重，异常显示状态并允许人工重试。请求接收与调度方式根据在线环境确定；长轮询、SSE、WebSocket 和多执行器调度不作为第一版前提。

在线响应器的资料检索与权限检查需要在其在线环境执行，并处理资料更新、删除、授权撤回和凭据隔离。在线响应器不要求持续调用模型，也不要求每位成员拥有独立服务器；在线共用 LangChain 响应核心，每次请求加载成员配置并创建独立执行上下文，具体并发与调度实现另行设计。

请求方取得请求 ID 后可以继续工作或结束会话。返回结果由通信服务保存，原会话仍可用时查询，否则在后续会话读取。第一版不承诺向已经结束的工作会话自动插入回答。

## 部署组合与替代路线

已确认首版面向能维护服务器的群组管理员。管理员准备服务器、域名、HTTPS、模型账户及持久存储，按部署文档完成安装、更新与备份恢复。普通成员通过桌面应用与工作 Agent 接入。面向没有服务器经验的部署者的安装引导与自动维护体验后续评估。

通信方式、响应器部署和资料访问是三个独立选择。通信可以经过群组服务、直接连接成员或经过成员各自维护的服务；响应器可以运行在本机、成员控制的在线环境或群组统一部署环境；资料可以保留在本机、按请求读取在线来源，或同步为授权副本。群组监督和共享空间整理可以与这些组合分别搭配。

资料在线不等于响应器在线。本地响应器即使能够读取在线资料，也无法在本机关闭后执行回答；要在成员电脑关闭后回答，仍需一个能够运行并访问获准资料的在线执行环境。

| 方案 | 优势 | 代价及适用条件 |
| --- | --- | --- |
| 群组服务 + 本地响应器 + 本地或在线资料 | 无需另外部署个人在线执行环境；资料与策略由成员管理；群组统一保存异步请求 | 回答等待成员本机运行；在线资料接入仍需连接器和凭据管理。适合允许等待的首批试用 |
| 群组服务 + 成员在线响应器 + 在线原始资料 | 成员电脑关闭后仍可回答；无需专门同步一份完整资料副本；可保持成员执行环境独立 | 每次回答依赖来源可用性、授权和接口；需要管理在线运行环境、凭据、限流及检索缓存。适合首批资料本来就在在线系统中的群组 |
| 群组服务 + 在线响应器 + 授权资料副本 | 回答不依赖成员电脑或原始来源当时可用；可预先限定资料并建立稳定索引 | 必须维护更新、删除、授权撤回、衍生索引和版本；复制可能扩大资料暴露范围。适合资料相对稳定且愿意维护副本的成员 |
| 群组服务统一托管响应器及授权资料 | 成员接入操作少，部署和观察统一 | 群组部署方承担凭据管理、资料隔离、执行额度和故障恢复；成员对执行环境的控制需要由接口与权限实现。适合以使用便利为首要目标的试用 |
| 点对点通信 + 成员响应器 + 群组监督与整理 | 成员直接交换资料，群组通信节点故障时仍可能直接交流 | 跨网络连接可能需要发现、打洞或中继；双方离线仍需队列或在线保存节点；监督依赖可靠上报。适合直接通信本身构成核心需求的情况 |
| 成员服务互联 + 群组监督与共享空间 | 成员独立管理服务、资料和执行；成员电脑关闭后可以由在线成员服务回答 | 需要维护多个服务、身份和权限配置，并协调消息去重、协议版本、重试及记录上报。适合已有个人服务的成员 |

点对点连接解决网络传输，不自动提供离线保存、群组权限或完整监督记录。libp2p 的连接机制包含 NAT 检测、打洞和中继，直接连接受限时可以使用中继。[libp2p 连接说明](https://docs.libp2p.io/connectivity/)

授权副本需要区分原始资料、索引、摘要和已发布回答。授权撤回应阻止后续使用并按规则清理副本及衍生数据；已经提供给其他成员的回答则按通信与共享内容的撤回规则处理。副本新鲜度需要在回答中展示来源版本和最后同步时间。例如 Google Drive 提供变更列表和分页令牌，连接器仍需把这些变更应用到自己的副本与索引。[Google Drive 变更接口](https://developers.google.com/workspace/drive/api/guides/manage-changes)

### 监督与自动整理

共享空间自动整理由群组配置的整理 Agent 统一负责，来源为留言板、已有共享内容和获准的定向求助记录；成员及其 Agent 可以提交内容和纠正建议。收录条件分别为不同成员重复出现的信息需求，以及管理员或群组规则明确指定的必需内容；具体人数与统计时间范围根据运行情况调整。重复需求按管理员配置的周期批量整理，明确指定的必需内容及已有条目的纠正、到期和撤回事件及时处理。

已确认按重复信息需求寻找一位或多位成员的有依据解答，并形成保留来源、适用范围和时间信息的候选条目；解答不足的重复问题继续作为未解决需求。发布分别遵守各内容提供者的授权，预先允许向全组分享的内容自动发布，授权不明确时展示具体候选条目并请求确认。

留言板由成员响应 Agent 按成员预设的关注主题、查看频率和参与额度自动查看并自主回答，允许多位成员回答同一个问题，无人参与的问题继续显示为无人回答。问题具有明确的有效等待期限，提问者可以提前标记已解决或无需继续回答；等待结束后停止为该次求助自动生成回答，交流记录仍按保留规则保存。

留言板查看和回答消耗归属于参与成员的独立留言板参与额度，共享空间整理消耗归属于管理员设置的群组整理额度，两者均受群组总消耗上限约束。留言板回答不自动消耗提问者的求助额度。

已确认失效或错误的共享内容立即从默认检索与自动回答依据中移除；尚未证实的反馈标记为有效性待确认，停止作为确定结论使用。群组整理 Agent 协调内容提供方的 Agent 排查问题，确认有效或修订后有效则保留，否则删除条目。明确的到期条件或有依据的纠正可以触发自动处理；版本变化只影响部分适用范围时，修订适用条件。

排查默认使用提供方既有授权的资料检索、依据检查与解释能力；重新运行实验、安装软件或修改工作文件须由提供方成员明确授权具体操作。整次排查使用群组整理额度，同时遵守提供方响应资源上限；管理员设置单次排查额度和等待期限，到达期限或额度上限仍无法确认有效则删除条目。后续获得充分依据时，可重新生成候选条目并按发布规则收录。

条目删除清理正文、专属依据副本及历史正文，只保留条目标识、删除时间和原因等最小处理记录。原始交流按各自规则保留，其他有效条目仍使用的依据继续保留。

必需内容发布或重要更新时通知全体成员，默认不要求确认已阅，管理员可以针对具体内容要求确认；通知送达、Agent 读取和成员确认分别记录。共享条目独立保存获准依据及来源、版本和时间信息，不依赖原交流持续保留；向全组展示依据须取得相应授权。

通信监督和共享空间整理是不同职责，可以在 MVP 中由同一个进程承担，但需要不同权限。监督读取获准通信并标记违规；整理提取可复用内容并维护来源、适用范围与版本。监督 Agent 能够读取定向记录，不自动获得向全组发布记录内容的权限。

自动发布可以依据成员预先授权的规则执行，无需要求成员逐条审批。范围不明确的内容先保存为参与方可见的整理草稿。整理后的摘要仍应保留原始依据；新回答与已有条目冲突时，应标记冲突，不能仅凭时间较新就覆盖已有结论。

在点对点方案中，上报通信与传递通信是两件事。请求 ID、双方回执、重试和待上报状态可以提高上报可靠性，但摘要上报不能支持检查完整原文，客户端故意绕过上报也不能由监督 Agent 单独发现。若要求每次通信在送达前受到检查，需要受控通信路径；若允许事后监督，则需要明确监督只覆盖实际上报的记录。

当前已确认在群组自行部署的环境中统一运行在线响应器并保存授权资料副本，采用指定目录自动同步；本地目录为权威来源，删除或移出获准范围后撤回在线使用。原始来源离线时，继续使用最近一次成功同步的副本。求助与回答统一经过群组 HTTPS 服务，具体同步实现、清理时限及备份清理规则仍待确认。其他组合保留为方案比较。

### 资料接入与个人 Agent 体验

手动上传、指定目录自动同步和自动筛选资料属于不同的资料接入方式，不必改变产品帮助成员获取彼此资料与经验的核心定义，但会改变成员需要承担的日常操作及系统责任。手动上传要求成员维护一组资料；目录同步要求成员授权持续访问已有资料来源；自动筛选要求系统根据规则判断哪些工作内容适合纳入资料。

已确认采用指定目录自动同步。成员首次选择已有目录并设置筛选与分享规则，本地组件在运行且联网时自动同步获准资料变更；后续符合规则的新增资料也自动同步，并可用于向指定群组回答。在线响应器使用最近一次成功同步的副本回答，成员无需逐次上传或逐份重新授权。授权范围内的自动解析与检索索引为当前实现建议。

本次同步成员明确选定的可分享文件。范围由目录、文件格式及文件或子目录排除规则确定，成员负责将适合分享的文件纳入范围；内容筛选可以辅助检查，但不自行扩大分享授权。混合资料的自动提取、脱敏及候选副本确认流程留待后续交付。

复制到个人在线副本与允许向其他成员回答是不同授权。首次配置应明确说明选定目录内符合规则的后续新增资料也会进入同步与回答范围；每次回答仍受成员配置的分享范围、回答策略和额度约束。成员可以选择已有目录或专门目录，无需为产品重新整理一套文件。资料副本的同步不自动授权将资料发布到群组共享空间。

首版在所连接的部署内，按目录授权向该部署的群组分享，并允许成员排除文件或子目录。目录内其余符合格式与筛选规则的资料使用相同分享范围，包括后续新增文件。多个部署之间的资料同步与授权分别配置方式待确认。

自动处理可以先包括解析、索引和回答时检索。根据工作会话主动提炼经验、扩大采集来源或自动向全组发布内容，需要另外定义规则。减少使用摩擦的效果仍需观察用户实际配置、维护和审查过程。

首版仅同步和使用 Markdown 与纯文本。分享资料目录是内容与范围的权威来源，在线副本不独立接受内容修改；本地删除、移出获准目录或被筛选规则排除的文件，在线响应器应停止在后续回答中使用其副本。资料副本的撤回不自动撤回已经发出的回答或已发布的共享内容。

目录暂时无法访问、电脑关闭或扫描失败不等于文件删除。在线响应器继续使用最近一次成功同步的副本，回答中展示所用来源版本与同步时间，不因来源离线时间较长自动暂停使用。原始来源离线时，在线服务无法知道尚未同步的本地修改或删除；收到删除或排除变更后，停止在后续回答中使用相应资料。本地目录仍是权威来源，在线副本只反映已成功同步的目录状态。撤回后先停止使用再清理正文副本、索引及摘要已确定；撤回生效的同步时机、索引失效处理、具体清理时限及备份清理需要在实现设计中确定。

服务收到资料删除、排除或授权撤回后，先停止后续使用并阻止仍依赖该资料的候选回答提供，包括等待成员确认的回答，再清理在线正文副本、检索索引和资料摘要，只保留资料标识、撤回时间及处理状态等必要记录。撤回生效与内容清理完成分别展示；备份清理规则及具体清理时限继续确定。

因撤回而失效的候选回答默认在同一次请求的剩余额度及等待期限内，按当前获准资料重新检索、生成并检查，消耗仍累计到原请求。当前资料不足时明确返回依据不足；自动重新生成次数及额度或期限耗尽时的结果继续确定。已经提供的定向请求、回答及获准引用按群组统一配置的期限保留，到期清理正文和引用，可以保留不含正文的请求状态与用量记录。副本撤回不自动撤回已提供内容；具体保留期限继续确定，见 [ADR-0011](../adr/0011-material-withdrawal-answer-retention.md)。

本地同步通过轻量桌面应用配置和管理，首版同时支持 macOS 与 Windows。分享规则采用目录级群组设置及文件或子目录排除。Electron 桌面框架已确认，开机启动方式与打包分发仍待确定。

### 工作 Agent 接入方式比较

接入目标是尽可能使用与 Agent 产品无关的接口，让具备相应调用能力的工作 Agent 发现成员、提交求助、读取回答。实际接入仍取决于宿主支持的协议、传输、认证和工具执行能力；接入某个协议不意味着可以控制工作 Agent 生命周期或读取其完整会话。

| 方式 | 定义与优势 | 代价及限制 | 当前建议 |
| --- | --- | --- | --- |
| MCP 服务器 | 按标准暴露工具、资源与提示模板；支持 MCP 的宿主可以发现和调用同一组求助工具 | 需要宿主支持相应传输与认证；工具可用不保证 Agent 主动求助、采用回答或提供采用证据 | 已确认的首版 Agent 入口 |
| HTTPS JSON API 与 OpenAPI 描述 | 独立于 Agent 产品的服务接口；OpenAPI 描述请求、响应与认证，便于自建 Agent、工具适配与集成 | Agent 宿主不一定允许直接 HTTP 调用或自动导入 OpenAPI；工具说明与安装仍需配套 | 独立公开接口留待实际需求决定 |
| CLI | 本地命令调用同一服务并返回结构化结果；允许执行命令的 Agent 可使用，也便于人工验证 | 需要安装与认证；云端或限制命令执行的宿主无法直接使用 | 首版不提供 |
| Agent Skill | 通过 SKILL.md、参考资料及可选脚本提供何时求助、怎样准备背景和怎样使用回答的流程说明 | Skill 自身不提供网络传输或权限执行，产品能力仍通过 MCP 调用 | 可选使用指导，不作为调用前提 |
| A2A | 标准化独立 Agent 服务的发现、交互、任务与结果交换，适合成员自托管响应器等互联需求 | 工作 Agent 宿主仍需具备 A2A 调用能力或适配；引入另一套协议与兼容验证工作 | 后续按独立服务互联需求增加 |
| 产品专用插件 | 可以使用特定宿主的界面、事件或上下文接口，提供更深的集成 | 每个产品需分别开发与维护，使用记录能力也由宿主决定 | 按实际需要增加 |

成员已有的工作 Agent 是主要求助入口，已确认由群组部署的远程 MCP 服务器提供产品能力，Skill 为可选使用指导，首版不提供 CLI。统一 HTTPS 群组服务承担业务状态、权限和额度，MCP 适配层可以与业务服务部署在同一应用内。服务内部可以复用发现成员、提交请求和读取结果等业务操作；是否独立公开 JSON API 与 OpenAPI 描述另行决定，不作为 MCP 接入的前提。[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture)、[OpenAPI 规范](https://spec.openapis.org/oas/latest.html)、[Agent Skills 定义](https://agentskills.io/home)、[A2A 与 MCP 比较](https://a2a-protocol.org/latest/topics/a2a-and-mcp/)

桌面应用与查看界面承担配置和审查职责。成员通过桌面应用选择分享目录、配置分享范围与响应方式，并查看同步状态；通过查看界面审查上下文和阅读共享内容。日常求助与使用回答发生在已有工作 Agent 中。被求助成员由其授权的在线或本地响应器回答；在线回答不要求工作 Agent 同时在线。本地响应器由桌面应用运行，默认调用云端模型，系统不自行启动成员已有工作 Agent。

已确认首版使用群组部署的远程 MCP，通过 HTTPS 上的 Streamable HTTP 提供工具调用。成员在工作 Agent 中配置服务地址，通过 OAuth 浏览器登录授权完成连接，无需安装本地 MCP 程序；本地 stdio 适配留待实际兼容需求决定。首版通过提交请求返回请求 ID、另一次调用查询状态与结果实现异步求助，不要求宿主支持额外的异步任务扩展。[MCP 架构与传输](https://modelcontextprotocol.io/docs/learn/architecture)

### 远程 MCP 身份认证

已确认采用 OAuth 浏览器登录授权作为远程 MCP 的默认认证方式。成员添加远程 MCP 地址后，由支持相应授权流程的宿主引导打开浏览器，登录该部署中的成员账户并授权连接；服务根据获得的访问令牌识别成员。成员身份用于检查群组资格、定向记录权限和成员求助额度，工具参数中的成员标识不能替代认证身份。

实现遵循 MCP 的标准 HTTP 授权机制。OAuth 授权服务可以与群组服务部署在一起，也可以使用独立服务；具体认证组件、客户端兼容策略及令牌有效期另行选择。手动配置个人访问令牌不作为默认接入流程，是否提供此类兼容入口根据实际需求决定。[MCP 官方授权规范](https://modelcontextprotocol.io/specification/latest/basic/authorization)

已确认首版采用管理员邀请制的本部署账户密码登录。成员在浏览器登录后授权 MCP 客户端，管理员负责邀请与账户恢复。账户登录与 MCP OAuth 授权分别由成熟组件实现，具体认证组件、客户端兼容及令牌有效期继续确定。

### 后端语言比较

TypeScript／Node.js 与 Python 都可以实现业务服务、远程 MCP 和多轮工具调用。候选 TypeScript 方案由 Node.js 承担在线业务及响应逻辑，桌面采用 Electron，可复用同一响应核心；Python 组件负责文件转换。候选 Python 方案由 Python 承担业务及响应逻辑，直接复用转换库，桌面若采用 Electron，则需要通过本地组件通信连接界面与 Python 响应核心。

已选择 TypeScript／Node.js 作为群组业务服务与在线、本地响应核心语言，Python 专门提供本地文件转换工具。该选择便于复用业务与响应流程代码，桌面已确认采用 Electron。不以语言选择推断模型能力或未经测量的性能。

### 响应器执行范围与模型配置

#### 响应核心 SDK 与框架比较

已确认响应核心采用 [LangChain JavaScript createAgent](https://docs.langchain.com/oss/javascript/langchain/overview)。它提供现成模型与工具循环，底层使用 LangGraph，满足当前受限资料查询需要。成员同时希望积累用于求职的 LangChain 实践经验，这是本次选择的明确理由。下表保留与 [AI SDK ToolLoopAgent](https://ai-sdk.dev/docs/agents/overview) 及 [LangGraph JavaScript](https://docs.langchain.com/oss/javascript/langgraph/overview) 的比较。

| 选项 | 当前流程的实现方式 | 主要权衡 |
| --- | --- | --- |
| AI SDK ToolLoopAgent | 复用模型与工具循环，产品代码负责分享检查、候选回答与业务状态 | 常规循环在内存中运行，中途崩溃恢复需产品自行处理；适合接受查询阶段重试的首版 |
| LangChain createAgent | 复用预置 Agent，按需要配置中间件和 LangGraph 检查点 | 能复用更多 Agent 状态与恢复能力，需要理解消息、中间件及检查点和业务状态的关系 |
| 直接使用 LangGraph | 将查询、生成、分享检查及人工确认组织为图节点 | 控制流程明确，适合复杂分支及执行恢复；需要自行定义图状态、节点和恢复语义 |

AI SDK 另有 [WorkflowAgent](https://ai-sdk.dev/docs/agents/workflow-agent) 提供持久化与可恢复执行，当前官方文档要求额外 Workflow 运行时；不能将普通 ToolLoopAgent 的内存执行限制推广到全部 AI SDK 能力。首版候选不默认引入这一额外运行时。

首版没有必须从中途工具步骤恢复的要求。默认允许重新执行未完成的查询，已生成候选回答、分享检查结果与待确认状态可靠保存；重试继续遵守当前授权与剩余额度。成员批准候选回答后，由产品重新检查必要授权并提供回答，该等待不必发生在工具循环内部。暂不要求自定义 LangGraph 图或持久 Agent 检查点，未来需要中途恢复时再增加；框架状态不替代成员授权、请求调度、额度及重复提交控制。

首版在线响应器只提供授权资料检索与模型回答。资料检索限于被求助成员获准分享的资料，模型负责整理依据、解释与生成回答；首版不开放通用代码执行、联网搜索或第三方工具。

响应模型是在线响应器处理队友求助并生成回答所使用的模型，求助者额度则限制成员向队友求助产生的模型消耗。模型选择、调用凭据与求助额度需要分别定义，并采用一致的群组费用规则。

已确认由群组管理员配置可用模型列表、模型服务地址、API Key 和群组默认模型，成员可以为自己的响应器选择列表中的模型。未设置时使用群组默认模型，成员不自行提交 API Key。在线与本地响应器默认都调用云端模型。模型接口支持范围、凭据保存方式、模型被移除或调用失败时的处理，以及不同模型消耗对求助者额度的影响，继续确定。

成员的模型偏好与回答策略分别配置。A 向 B 求助时使用 B 选择的模型，或在 B 未设置时使用群组默认模型；调用费用记到群组配置的模型账户，消耗归属于 A 的求助额度。消耗按 Token 用量计量，具体扣除口径和求助者单次消耗控制待确认。

### 成员响应配置与团队响应服务

成员响应器、资料归属和服务部署是不同层面的设计。已确认首版共用群组在线响应服务，根据请求接收成员加载其资料授权、回答策略、响应模型与响应资源上限，每次请求创建独立执行上下文。成员无需分别运行独立进程或维护独立服务器，模型调用经过独立模型服务。

共用响应服务与成员独立响应服务都可以支持自定义配置。比较中的独立服务指每位成员拥有独立进程或容器，可以由群组统一托管，不要求成员各自维护服务器。

| 比较项 | 共用响应服务与多成员配置 | 每位成员独立响应服务与配置 |
| --- | --- | --- |
| 自定义能力 | 每位成员配置资料、模型、回答策略与资源上限；每次请求创建独立执行上下文 | 同样支持成员配置，还可以分别选择运行依赖和服务版本 |
| 资料与会话隔离 | 依靠服务端授权过滤及独立请求上下文执行，不能共用成员会话或对话历史 | 可以通过进程、挂载和凭据限制访问范围，隔离效果取决于实际配置 |
| 故障影响 | 服务进程故障可能影响全部成员，单次请求故障应单独处理 | 单个成员服务故障可以单独恢复；共用数据库、模型服务仍可能影响多位成员 |
| 更新与运维 | 统一发布，服务实例较少 | 需要管理成员服务的创建、版本、状态与回收 |
| 适用需求 | 成员差异主要通过受支持的配置表达 | 成员需要独立依赖、服务版本、部署控制或执行隔离 |

已选择首版共用在线响应服务，保留成员独立响应配置与请求独立执行上下文。成员独立服务保留为未来需要独立运行依赖、服务版本或更强执行隔离时的替代方案。本地响应器采用产品提供的目录查询与解析工具，在线响应器继续限于授权资料检索与模型回答。

统一存储可以保留成员资料的归属与使用范围。资料副本可以由群组集中保存，检索仍按资料所属成员、分享范围与版本状态筛选。将所有资料保存到同一服务中，不自动授权全组直接读取，也不改变本地目录为权威来源的规则。

团队公共资料库与成员授权资料副本具有不同管理规则。前者提供已授权供群组共同使用的资料，可支持跨成员综合回答；后者保留成员控制的回答范围及策略。首版集中保存的是成员授权资料副本，检索按接收成员及其分享范围执行，不自动发布为群组公共内容。共享空间自动整理后续交付。

### 在线与本地混合响应

已确认资料访问采用混合策略。在线响应器依据已同步的授权资料副本回答，本地响应器访问成员授权但未同步的本地资料；成员可以保留只允许本地查询的资料来源，不要求把全部资料上传至群组服务。已确认成员预设本地查询范围，符合规则的请求交给本地响应器，其余优先使用在线副本，依据不足时可以请求本地补充。需要本地查询而本地不可用时保留待处理状态。已确认本地响应器由桌面应用运行并默认调用云端模型；模型调用经过独立模型服务，等待期限由求助者配置，具体模型调用授权继续在实现设计中确定。

已确认本地响应器提供多轮 Agent 工具调用。模型选择列出文件、搜索、读取与解析工具，桌面应用在成员指定的目录及资源上限内执行，再将结果提供给模型继续回答。首版工具由产品提供，不开放任意 Shell、Python 或成员自行添加的第三方工具；具体工具实现与解析器待选择。

首版本地响应器访问成员指定、未同步的本地查询目录，处理 Markdown、PDF、Word、Excel 与 PowerPoint 的可提取文字和表格。图像理解暂不支持，JPG、PNG、文档内图片与扫描件 OCR 留待后续；含图像的文档仍可处理其可提取文字，回答需说明相关视觉内容未参与分析。具体 Office 扩展名及解析深度继续确定。在线同步副本仍仅支持 Markdown 与纯文本，系统通讯录等非目录资料连接器留待后续场景评估。

成员配置采用目录与分享规则两个主要项目。分享规则可以通过分享偏好或分享 Skill 表达，规定允许与禁止分享的内容，不要求成员分别维护可读取和可分享的文件清单。指定目录内的必要内容用于模型处理，符合允许规则的回答自动发送；命中禁止规则时删减或拒绝提供；规则未覆盖或无法判断时由成员确认，禁止规则优先于允许规则。工具执行权限与资源上限由桌面应用执行，分享 Skill 不直接扩大这些权限。

分享规则的实现分为生成、检查和提供回答三步。提供回答指将最终正文、引用及来源信息置于该次求助的请求方可读取的状态；自动提供表示无需资料所属成员逐次批准。必要资料片段提交给模型处理发生在生成与检查过程中，遵守目录配置中的模型处理授权。回答生成时加载成员的规则版本，候选回答及准备提供的引用、来源名称一同接受检查。已确认自动提供回答前增加一次独立模型检查调用，检查正文、引用及来源信息，返回允许、拒绝或需要确认及对应规则依据；能够用明确模式表达的禁用字段另由程序检查。检查调用的消耗计入同一次求助及其资源上限。提供回答的程序只接受通过检查的最终内容，检查失败、规则无法判断或规则版本已变更时停止自动提供。语义规则的判断质量需要实际样例验证。

已确认 Office 与 PDF 转换为 Markdown 作为本地响应器的一项工具。Agent 按需要调用该工具，桌面应用检查目录权限与文件版本，执行本地转换并返回可供搜索与读取的结果。优先评估微软 [MarkItDown](https://github.com/microsoft/markitdown)，其官方说明提供 Python 转换库，列出 PDF、Word、Excel 与 PowerPoint 支持，并提供按格式安装的依赖。应用内置转换组件，不要求成员自行安装 Python，不启用图像描述、OCR 或云端文档转换；转换产物作为本地查询缓存，不自动同步为在线副本。缓存需关联原文件路径、版本与可提供的来源位置，转换失败和不完整解析应明确返回。该工具尚未安装或用本项目样例验证，具体版本、格式范围与桌面打包实现待验证。

本地响应器默认调用云端模型。桌面应用根据请求读取必要的获准本地资料，调用云端模型按成员的回答策略和分享规则生成答案，再通过群组服务提供给求助者。资料仅在本地保存，不要求为支持回答而将完整来源同步为在线副本。

自动回答使用成员明确获准分享的资料范围。例如，绘画 Skill 同时包含方法与私人经历，成员没有明确授权分享的提炼内容须由本人确认具体回答后发送。仅凭模型判断内容可分享，不能扩大既有授权；隐私与经验混合场景尚未实现或验证。

本次成员确认页面展示求助问题、候选回答及准备提供的引用和来源信息，资料所属成员可以批准或拒绝，候选回答编辑留待后续。批准只针对页面展示的具体候选内容；提供回答前重新检查当前授权及请求有效性，来源撤回继续按当前获准资料重新生成的规则处理，批准不允许发送已经失效的候选内容。成员拒绝后，该次求助返回未获准提供的结果。确认通知与页面接入方式继续确定。

请求统一经过群组 HTTPS 服务，在线与本地结果按同一请求关联。两条路径按成员预设范围选择，具体规则表达方式、同次请求的执行协调、额度累计与待处理请求的有效期继续确定。已有远程 MCP 求助入口不自动提供本地请求接收能力，日常工作 Agent 的生命周期仍由成员管理。

### 模型调用 SDK 与模型网关候选

多个逻辑响应器可以共用同一套模型调用组件。响应器按成员配置选择资料、回答策略与响应模型，业务服务负责身份、资料授权和请求状态。模型调用组件负责调用管理员配置的模型服务并返回文本与用量；群组不因拥有多个响应器而必须自行部署模型推理服务。这是当前设计判断，尚未实现或验证。

模型调用 SDK 可以嵌入业务服务，减少不同模型接口的适配工作。AI SDK 提供模型提供商适配包、模型注册与别名配置，并返回生成文本及用量；适用于后端选择 TypeScript 时的候选方案，使用提供商适配包直接调用模型服务不要求使用托管网关。[AI SDK 提供商接入](https://ai-sdk.dev/docs/getting-started/choosing-a-provider)、[模型管理](https://ai-sdk.dev/docs/ai-sdk-core/provider-management)、[文本生成与用量](https://ai-sdk.dev/docs/ai-sdk-core/generating-text)

独立模型网关可以集中代理多个提供商。LiteLLM Proxy 提供统一接口、调用记录、虚拟 Key 及预算管理，但会增加一个部署服务；其文档中的持久预算机制需要 PostgreSQL，金额预算与 TPM 速率限制也不等同于本项目选择的累计 Token 求助额度。本项目仍需执行请求方消耗归属、提供方资料权限与响应上限。[LiteLLM 网关](https://docs.litellm.ai/docs/simple_proxy)、[预算与限速](https://docs.litellm.ai/docs/proxy/users)

Bifrost 是独立网关的另一候选，提供多提供商接入、管理界面和虚拟 Key。官方文档支持单节点使用 SQLite 保存配置，其 Token Limits 按周期限制输入与输出 Token 累计用量，比每分钟吞吐率限制更接近周期求助配额。该机制仍需与请求方身份、全组 Token 上限和人工补充规则对应；不能仅凭文档认定已满足项目额度规则。[Bifrost 部署与配置](https://docs.getbifrost.ai/quickstart/gateway/setting-up)、[预算与 Token 限制](https://docs.getbifrost.ai/features/governance/budget-and-limits)

Python 后端也可以采用 LiteLLM SDK，在应用内复用提供商适配能力。SDK 与独立 Proxy 是两种接入方式。Python 后端作为比较方案保留，当前业务与响应核心已选择 TypeScript／Node.js。[LiteLLM SDK 与 Proxy](https://docs.litellm.ai/docs/)

已确认独立模型服务供在线响应器与桌面应用共同调用。群组服务管理成员身份、求助请求、资料授权、响应调度与消耗归属；模型服务管理提供商凭据、模型调用认证、可用模型与用量记录。在线响应器通过模型服务生成回答，桌面本地响应器将必要片段发送到模型服务，再将获准回答提交群组服务。本地片段经过模型服务及模型提供商处理，其日志与保留规则需要明确。

首版桌面模型调用限于产品内求助响应，必须与服务端认可的求助请求关联。A 向 B 求助时，B 的桌面应用执行回答，消耗归属于 A；不能仅按调用凭据所属成员扣除额度，也不能接受桌面端任意指定扣费对象。候选方案是群组服务在检查权限与额度后签发绑定请求、模型、有效期和用量上限的调用授权，由模型服务验证并执行；现成网关能否直接满足该授权语义，仍需选择后验证。

独立模型服务已确认，具体网关产品与调用 SDK 待选择。独立模型服务可以与群组服务运行在同一台服务器，服务职责分离不要求分开购买服务器。

### 群组模型费用与成员求助额度

群组模型费用与成员求助额度承担不同职责。模型调用费用记到群组配置的模型服务账户；成员求助额度用于限制各成员向队友求助产生的消耗。已确认提供全组消耗上限和每位成员的求助额度，默认启用，管理员可以调整或关闭；关闭限制后仍记录实际消耗。按模型服务报告的实际总 Token 累计，不同模型不按价格加权，缓存与推理 Token 明细按提供商字段处理且不重复相加。成员额度按月分配，管理员可以调整与补充，初始额度、群组总额及单次请求上限作为管理员配置项。同一次求助中的查询、回答生成、分享检查及重试均累计在该请求，本地响应同样归属于求助者，提供方资源上限独立生效。月度切换的结算细节及并发预留继续由具体实现设计确定。

需要等待本地响应时，默认等待时间由求助者自行配置。求助者配置自己发出请求的默认等待时间，可按次调整；提交时保存明确截止时间，并在后续调度与提供回答时检查有效性。

定向求助消耗求助者额度，提供方的响应资源上限独立生效。A 向 B 求助时，消耗记到 A，B 继续控制资料、回答策略及单次与累计响应资源上限。启用成员求助额度限制时，提交请求检查 A 的额度，不足则返回明确原因，由管理员补充后重新提交。关闭群组或成员额度限制，不改变 B 的资料权限与响应资源上限。留言板参与消耗归属于参与成员，共享空间整理消耗归属于群组，使用各自独立额度并受群组总消耗上限约束。群组总预算不足、模型服务账户余额不足、失败重试和执行时额度不足的处理仍待确认。

## 审查与验证

上下文审查应当展示当前任务的求助目的、提供成员、获得的具体内容、来源版本与时间，以及能够定位的后续采用情况。通信返回只能证明内容已提供；工作 Agent 的采用报告与实际输出或行动需要分别标明，缺少证据时显示采用情况未知。信息相关也不自动证明任务结果已经改善。

通信监督提供检查和处理依据，接收方个人服务仍需独立执行资料权限、工具限制和额度。通信分析不能代替这些执行限制，具体监督与处理机制尚待确定。

建议用一次离线求助验证部署方案：B 先上传授权资料副本，再关闭电脑；A 提交问题，B 的在线响应器在授权范围和额度内依据副本回答；A 读取结果并审查来源版本及副本时间；普通成员 C 无法读取这次定向通信。只有符合分享规则的内容才能进入共享空间。

这项验证尚未执行。文档中的技术建议不代表已经实现、已经通过测试或已经证明产品有效。
