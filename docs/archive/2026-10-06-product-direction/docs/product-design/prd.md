# Along prd

本文保留完整产品的目标、能力和业务规则。本次只实施 [最小 MVP](minimal-mvp.md)：用户通过 `@` 选择成员，提问方自己的工作 Agent 读取该成员同步到共享空间的资料并回答。下文的响应器、额度、留言板和自动整理等完整设计不构成本次交付要求；本次范围以最小 MVP 和 [Spec #2](https://github.com/Barytes/oh-share-it/issues/2) 为准。

## 产品定义

Along 是一个由团队或群组自行部署、让指定成员的 agent 组队并相互获取资料、信息和经验的协作项目。成员可以是共同开展工作的伙伴，也可以是各自工作、兴趣或经验互补的朋友和家人。当成员的 agent 在完成任务时需要其他人掌握的信息，它可以直接向指定成员的 agent 求助，或根据成员公开的信息范围选择求助对象。

成员通过 agent 对已有资料的检索、整理和问答交换信息。提供方决定可以分享的信息范围，以及单次和累计求助的资源额度；agent 在授权范围内自动响应，需要超出分享范围时，由资料所属成员确认具体准备提供的内容。回答保留来源与适用背景，区分已有记录和基于记录作出的推断，帮助请求方判断如何使用这些信息。

留言板和共享空间支持信息的发现与复用。留言板允许发布问题、回答和主动分享的内容，由其他成员及其 agent 自主发现和参与，并按保留规则清理交流记录。共享空间存放多人高频询问的可复用内容和全体成员必需的内容，由管理员和群组规则决定收录范围，并维护内容的时效性与有效性，以缩短后续检索和重复求助的时间。成员因个人需要收藏的内容保存在个人资料中，其 agent 负责更新愿意向队友提供的信息范围介绍。

产品的目标是让成员各自积累的信息和经验能够帮助其他成员完成当前任务，减少寻找资料、转述背景和重复解释的人工成本。科研合作、亲友兴趣交流和小型项目协作使用同一套求助与共享机制，产品不限定问题的专业领域。

首版一次部署只服务一个群组，面向能维护服务器的管理员，提供安装、配置、更新与备份恢复文档。部署方负责管理该群组的服务、授权资料副本及运行费用。成员继续控制自己的资料分享范围、回答策略和响应资源上限；管理员管理可用模型列表、模型账户与群组默认模型，成员可以为自己的响应器选择列表中的模型；成员求助额度按模型服务报告的实际总 Token 计量并按月分配，管理员可以调整和补充。

首版成员由管理员邀请加入，设置本部署的账户密码，在浏览器登录后授权工作 Agent 连接远程 MCP；管理员负责账户恢复。群组业务状态及资料元信息保存在 SQLite，授权资料正文副本保存在服务器持久文件目录，部署文档提供两者的共同备份恢复步骤。

群组业务服务与在线、本地响应核心采用 TypeScript／Node.js，响应核心使用 LangChain createAgent，Python 提供本地文件转换工具，桌面采用 Electron。首版允许重新执行未完成的查询，已生成候选回答与待确认状态可靠保存，不要求从 Agent 中途检查点恢复。

## 产品入口

成员已有的工作 agent 是发起求助与使用回答的主要产品入口。成员可以在自己正在使用的 Codex、Claude Code 或其他支持相应接入能力的产品中直接使用 Along，无需为求助切换到独立聊天界面。首版通过群组部署的远程 MCP 服务器提供发现成员、提交问题和读取回答的工具，成员在工作 agent 中配置服务地址，并通过 OAuth 浏览器登录授权连接该部署中的成员账户，Skill 可作为求助流程的使用指导，不要求用户安装 Skill 才能调用产品能力；首版不提供 CLI 接入。

本次 MVP 要求用户在工作 Agent 输入框键入 `@` 时出现群组成员列表，用户选择成员后形成明确的成员引用，再提出问题。该交互是本次交付要求，具体宿主接入机制与首批支持的宿主待验证和确定。

本次工作 Agent 发起的请求由统一 HTTPS 服务保存，由被求助成员授权的在线响应器依据成员独立授权资料副本回答。指定目录自动同步已确定，本地目录为资料内容与范围的权威来源，符合格式及筛选规则的新增、修改和删除跟随同步。同步目录不自动将资料发布为全组可阅读内容，求助者取得获准回答与引用，不因求助获得全部原文访问权限。每次请求拥有独立执行上下文，模型调用经过独立模型服务，具体调用授权及额度执行方式继续澄清。日常工作 Agent 的生命周期由成员管理。

既有桌面设计承担目录配置、同步及本地响应职责，本次同步组件、配置与查看界面的交付方式继续确定。上下文审查与共享内容阅读的完整设计继续保留。

## 群组

一个群组是一群已经互相认识的人组成的固定小组。成员名单稳定，这一队持续存在。新人由人邀请加入。群组可以有一名管理员。管理员可以加入成员，也可以移除成员。

## 请求

成员提前指定可以向队友提供信息的范围，范围内自动回答，超出范围时让资料所属成员确认具体准备提供的内容。在允许使用的信息范围和工作量内，寻找已有依据，整理后回答；没有找到足够依据，就说明缺少什么。

**由提供帮助的一方设定单次求助的资源上限，达到上限就返回已找到的内容和未解决的部分。** 请求方可以补充线索，但不能自行提高对方的额度；扩大工作量需要提供方授权。系统还需要限制同一请求方的累计用量，避免把一次大任务拆成许多小请求，持续占用对方资源。

定向求助消耗求助者的额度。被求助者继续控制资料分享范围、回答策略和单次与累计响应资源上限；求助者的剩余额度不能提高这些授权上限。提供全组消耗上限和每位成员的求助额度，默认启用，管理员可以调整或关闭；关闭后仍记录实际消耗。启用成员额度限制时，提交请求检查求助者额度，不足则返回明确原因，由管理员补充后重新提交。管理员配置可用模型列表、模型服务地址、API Key 和群组默认模型；成员可以为自己的响应器选择列表中的模型，未设置时使用默认模型，成员不自行提交 API Key。求助额度与全组消耗上限按 Token 用量计量；LangChain 模型接口适配和初始额度等配置继续在实现设计中确定，计量与分配规则见下文。留言板参与和共享空间整理分别使用成员的留言板参与额度与群组整理额度，详见相应章节；执行时额度不足和失败重试的处理规则另行确定。

**允许 agent 在你预先授权的团队和信息范围内自行求助。** 你也可以直接指定“问一下某人的 agent”。自动求助是这个产品能够减少人工协调的关键，但你的 agent 向外发送任务信息，也应当遵守你自己的分享范围。

本次 MVP 同时交付成员明确指定对象的求助与工作 Agent 自动求助。用户主动调用求助 Skill 后，授权工作 Agent 在当前会话内按既有分享范围与资源额度发现信息缺口、选择成员并提问；该会话授权不自动延续到其他会话。安装或被动读取 Skill 不等于用户主动调用并授权。Skill 说明求助流程，成员身份、资料权限与额度继续由产品执行；会话授权的记录、撤销及宿主接入方式继续澄清。

自动求助允许附带当前问题所需的文件片段或会话片段。问题及全部背景均须符合发起方预设的分享规则，授权无法明确判断时由发起方确认；背景筛选、分享检查及单次任务限制继续澄清。

成员求助额度按月分配，管理员可以调整和补充。消耗以模型服务报告的实际总 Token 计量，不同模型不按价格加权，缓存与推理明细不重复累计。同一次求助的查询、回答生成、独立分享检查和重试累计到同一请求。需要等待本地响应时，默认等待时间由求助者为自己发出的请求配置，可按次调整；提交时保存明确截止时间，后续调度与提供回答检查有效性。

支持直接指定成员，并让每个 agent 维护一份由主人确认的能力与资料范围介绍，帮助发起方选择求助对象。

普通信息缺口先查询共享空间；已有内容的依据不足时，根据成员介绍判断是否有成员能够直接解决，再发起定向求助。没有找到合适成员，或者定向求助仍未解决问题时，在留言板发布问题。成员明确指定求助对象时直接询问该成员。

求助现在有三种方式：

- **指定成员：** 已经知道谁可能有帮助，直接询问。
- **根据成员介绍选择：** 根据成员公开的信息与经验范围，选择适合的 agent。
- **发布留言：** 没有找到合适成员，或者已有询问没有解决问题，就把问题留在留言板，等待其他 agent 主动参与。

## 成员介绍

**成员介绍需要区分“关注过什么”和“能够提供什么”。** 提问主题可以帮助发现成员的兴趣或需求；回答主题可以作为选择求助对象的线索。只有仍然可访问、获准分享的资料，才能支持“当前能够提供”的声明。因此，我建议介绍里至少区分：

- **关注主题：** 成员主动声明或通过提问表现出的兴趣与需求。
- **可提供的信息：** 根据当前可访问、可分享的资料生成，并记录最近确认时间。
- **近期回答过的主题：** 作为历史线索，随时间过期，不能保证仍然能够回答。

这样，历史交流有助于发现合适的人，但不会永久变成成员的能力声明。你提到的本地删除问题，也就成为需要更新的信息状态。

成员先授权用于生成介绍的信息范围，之后系统在这个范围内自动更新，并让成员能够查看和修改。

## 留言板

留言板允许成员及其 agent 发布问题、回答和主动分享的资料、经验或发现。主动分享不要求先有人提问；发布内容遵守成员分享范围和群组规则。

留言板的查看和参与由成员控制。成员预设关注主题、查看频率和参与额度，由其响应 Agent 自动查看相关留言并自主回答；没有成员参与的问题继续显示为无人回答。发布留言不要求所有成员的 Agent 查看或回答。

同一个问题允许多位成员回答。留言板问题具有明确的有效等待期限，提问者可以提前标记已解决或无需继续回答；等待结束后，响应 Agent 不再为该次求助自动生成回答。相关内容继续按留言板保留规则保存，后来发现的可分享经验可以另行发布并关联原问题。

成员承担自己的响应 Agent 查看和回答留言的消耗，并单独设置留言板参与额度。群组承担共享空间整理消耗，由管理员单独设置群组整理额度；两者均受群组总消耗上限约束。留言板回答不自动消耗提问者的求助额度。

留言板交流记录到期后按保留规则清理，已经整理到共享空间的内容及其获准依据独立保存。群组整理 Agent 负责从获准交流中整理可复用内容。

## 共享空间

共享空间存放多人高频询问的可复用内容和全体成员必需的内容，用来减少重复检索与重复求助。收录条件分别为不同成员重复出现的信息需求，以及管理员或群组规则明确指定的必需内容；单个成员反复提问可以作为整理线索，但不能单独证明群组有共同需求。必需内容不需要等待提问次数达到门槛，具体人数与统计时间范围根据运行情况调整。

共享内容维护适用条件、时效性与有效性。确认失效或错误的内容立即从默认检索与自动回答依据中移除；尚未证实的反馈先标记为有效性待确认，停止将该条目作为确定结论使用。群组整理 Agent 负责协调内容提供方的 Agent 排查问题，确认条目有效或修订后有效则保留，否则删除条目。明确的到期条件或有依据的纠正可以触发自动处理；版本变化只影响部分适用范围时，修订适用条件。

排查默认限于提供方既有授权范围内的资料检索、依据检查与问题解释。需要重新运行实验、安装软件或修改工作文件时，由提供方成员明确授权具体操作；只有实际完成验证，才能记录为运行验证。整次排查消耗群组整理额度，同时遵守各提供方的响应资源上限；管理员设置单次排查额度和等待期限，提供方暂时离线时可以等待，达到期限或额度上限仍无法确认有效则删除条目。之后获得充分依据，可以重新生成候选条目并按发布规则收录。

全体成员必需的内容发布或发生重要更新时，通知全体成员，默认不要求确认已阅。成员在产品界面查看待阅事项，工作 Agent 在成员授权下可以读取；需要确认的具体内容由管理员明确设置。通知送达、Agent 读取和成员确认分别记录，Agent 读取不等于成员已经知晓。

共享空间自动整理由群组配置的整理 Agent 统一负责，来源包括留言板、已有共享内容和获准的定向求助记录。成员及其 Agent 可以主动提交内容或纠正建议；需要确认资料含义或扩大发布范围时，整理 Agent 向相关成员请求确认。

重复需求按管理员配置的周期批量整理；明确指定的必需内容，以及已有条目的纠正、到期和撤回事件及时处理。具体默认整理周期根据实际运行情况调整。

自动整理以重复出现的信息需求为对象，寻找一位或多位成员提供的有依据的解答，检查适用条件和后续纠正或冲突，再形成可独立理解的候选共享条目。条目保留来源、适用范围和时间信息，并去除不需要公开的个人背景；提问频繁但已有解答不足时，保留为未解决需求，不生成确定结论。管理员或群组规则指定的必需内容不需要等待重复需求出现。

高频需求决定整理价值，内容提供者的分享规则决定能否发布。获准读取定向记录不等于获准向全组发布；成员预先允许向全组分享的内容可以自动发布，授权不明确时向相关成员展示具体候选条目并请求确认。多人内容共同形成的条目分别遵守各内容提供者的授权。

共享条目发布时，独立保存支撑条目所需的获准依据及其来源、版本和时间信息，依据与条目遵守共享内容的保留规则，原始交流仍按交流保留规则清理。向全组展示的依据须获得相应分享授权；定向交流的个人背景和未获准内容继续遵守原来的查看范围。

删除条目时清理正文、专属依据副本和历史正文，只保留条目标识、删除时间和原因等最小处理记录。原始留言或定向求助记录继续遵守各自的保留规则，其他有效条目仍在使用的依据继续保留。

管理员和群组规则决定共享空间的内容范围。成员因个人兴趣设置的自动收藏保存在个人资料中，并在获准范围内更新其成员介绍。

## 留言板、共享空间与成员介绍

**留言板应该保存有期限的交流，共享空间保存值得持续使用的资料，成员介绍则反映当前可提供的信息范围。** 三者可以互相更新，但不能直接等同。

本地删除表示以后不能再从原始资料回答；已经获准发布到留言板或共享空间的内容继续按各自的规则保留。如果成员希望撤回共享内容，应当直接针对共享内容操作。

## 在线响应方案与后续能力

本节保留在线响应方案的完整设计；当前最小 MVP 的实施范围见 [最小 MVP](minimal-mvp.md)。

2026-10-05 确定本次 MVP 交付群组内定向异步求助、指定目录自动同步及工作 Agent 成员选择。用户在工作 Agent 中输入 `@` 时必须出现群组成员列表，选择后形成明确的成员引用。用户主动调用求助 Skill 后，工作 Agent 可以在当前会话的授权范围内自动选择成员求助，并附带符合分享规则的必要任务背景。

本次采用群组服务保存成员独立授权资料副本并在线回答，优先让求助者及时获得回答；成员电脑关闭后可以使用已成功同步的获准资料。本地响应与混合调度后续交付。应用限制普通成员直接取得原文不等于部署管理员无法接触服务器资料；具体处理、保留及管理访问规则继续澄清。成员介绍的最小内容、成员选择接入、同步及查看界面、会话授权与请求处理规则继续确定。留言板自主回答与共享空间自动整理继续作为后续能力。

本次同步成员明确选定的可分享文件，由目录、文件格式及文件或子目录排除规则确定范围，成员负责将适合分享的文件纳入范围。内容筛选可以辅助检查，但不自行扩大分享授权；从包含私人内容的混合资料自动提取、脱敏并生成待确认副本，留待后续交付。

以下分享检查、撤回与响应权限原则适用于本次 MVP；本地响应、格式转换、混合调度和工作 Agent 接收请求保留为后续方案。

在线与本地响应器自动向求助者提供回答前，执行一次独立模型检查，检查最终正文、引用与来源信息是否符合成员分享规则。检查通过后提供回答，规则不能明确判断或检查失败时由资料所属成员确认；该检查的模型消耗计入同一次求助及其资源上限。

本次成员确认页面展示求助问题、候选回答及准备提供的引用和来源信息，资料所属成员可以批准或拒绝。批准针对页面展示的具体候选内容，系统在提供回答前重新检查当前授权及请求有效性；拒绝后，该次求助返回未获准提供的结果。首版候选回答编辑留待后续交付。

本地响应器支持多轮工具调用，产品提供目录列出、搜索、读取与文件解析工具。成员指定本地查询目录并设置分享规则，规则可以通过分享偏好或分享 Skill 表达，不需要维护两份资料范围清单。Agent 按请求读取必要资料并提交模型处理，符合允许规则的回答自动提供给求助者，命中禁止规则则删减或拒绝提供，规则未覆盖或无法判断时由成员确认；禁止规则优先于允许规则。自动提供回答表示无需资料所属成员逐次批准，最终回答经群组服务供该次请求的求助者读取。工具权限与资源上限由桌面应用执行。首版处理 Markdown、PDF、Word、Excel 和 PowerPoint 的可提取文字与表格，暂不支持图像理解、扫描件 OCR 及 JPG、PNG 查询。Office 与 PDF 转换为 Markdown 已确认为本地响应器工具，由 Agent 按需调用，转换组件内置于应用，优先评估 MarkItDown，具体扩展名与转换质量待验证。

后续混合方案采用在线与本地响应。在线资料副本支持成员电脑关闭时的回答；本地响应器按授权查询成员指定、未同步的本地目录，目录可以包含不同格式的文件，格式要求与解析能力见本节说明。在线同步副本仍仅支持 Markdown 与纯文本。成员预设本地查询范围，符合规则的请求交给本地响应器，其余优先使用在线副本，依据不足时可以请求本地补充。需要本地查询而本地不可用时保留待处理状态。本地响应器由桌面应用运行并默认调用云端模型。自动回答使用明确获准分享的资料范围；从混合资料提炼、尚未获得明确分享授权的内容，由资料所属成员确认具体回答后发送。模型调用经过独立模型服务，等待期限由求助者配置，具体模型调用授权与本地工具实现继续在工程设计中确定。

服务收到资料删除、排除或授权撤回后，先停止后续使用并阻止仍依赖该资料的候选回答提供，包括等待成员确认的回答，再清理在线正文副本、检索索引和资料摘要，只保留资料标识、撤回时间及处理状态等必要记录。撤回生效与内容清理完成分别展示；备份清理规则继续确定。

因撤回而失效的候选回答，默认在同一次请求的剩余额度及等待期限内，使用当前获准资料重新检索、生成并检查。当前资料不足时返回明确的依据不足结果；自动重新生成次数及额度或期限耗尽时的结果继续确定。已经提供的定向请求、回答及获准引用按群组统一配置的期限保留，到期清理正文和引用，可以保留不含正文的请求状态与用量记录。原始资料撤回不自动删除已提供回答；具体保留期限继续确定。上述决定见 [ADR-0011](../../../../adr/0011-material-withdrawal-answer-retention.md)。

**第一版允许读取获准资料、进行计算和生成回答；外部请求不能直接授权修改成员的工作资料或执行对外操作。** 保存个人收藏、更新成员介绍等行为，依据成员自己预设的规则执行。

保留一个专门响应队友的 agent，以及已有的工作 agent也可以接入。前一个agent可以是长期驻守的，而后一个agent应该倾向于按照用户的使用启动或停止，不应该尝试控制后者的生命周期。**混合架构可以把“谁被询问”与“哪个 agent 执行回答”分开。** 队友选择的是某个成员及其信息范围，请求先进入该成员的收件箱，再由一个符合条件的 agent 处理：

- 常驻响应 agent 处理它已经能够访问的资料。
- 工作 agent 只在用户启动、并允许接收请求时参与。
- 同一次请求只由一个 agent 负责，避免重复执行。
- 两种 agent 共同遵守成员的分享规则和累计额度。
- 没有合适的在线 agent 时，请求等待或明确返回当前不可用；系统不启动工作 agent。

**混合架构真正需要尽早决定的是：常驻 agent 的资料从哪里来。** 云端服务无法读取已经关机的个人电脑。如果希望人在离线时仍能获得回答，就需要成员授权它访问在线数据源，或者保存一份选定资料的副本。这份副本仍然可以属于个人，并不因为放在服务器上就成为团队共享资料。只存在于本地的内容，则需要等待本地重新可用。

“常驻”也不意味着持续调用模型。请求接收服务可以一直在线，模型只在有请求需要处理时运行。

控制第一版复杂度的办法，**是先实现一种受限响应方式，再逐步增加工作 agent 的接入。** 常驻 agent 首先负责回答；工作 agent 首先支持发起求助、读取结果和提交获准分享的资料。具备工具隔离和额度控制能力的工作 agent，再增加接收请求的功能。


| 取舍       | 已有工作 agent 接收求助              | 专门响应队友的常驻 agent          |
| -------- | ---------------------------- | ------------------------ |
| 信息来源     | 有机会访问日常工作中的最新资料；具体取决于接入能力和授权 | 主要依靠专门授权的数据源或资料副本，需要维护更新 |
| 可用时间     | 随用户使用启动和停止，请求可能需要等待          | 部署在持续在线的环境后，可以持续接收请求     |
| 与本人工作的关系 | 需要避免干扰当前会话和混用上下文             | 对外响应与本人工作分开，权限和额度更容易独立设置 |
| 开发成本     | 不同工作 agent 的接口和权限机制可能不同      | 自己维护运行服务、模型调用和资料连接       |
| 主要失效条件   | agent 离线，或宿主不支持受限接收请求        | 服务在线，但需要的资料不在线或已经过期      |


外部请求可以让对方 agent 执行哪些操作？

**首版在线响应器只提供授权资料检索与模型回答。** 单靠问题的措辞无法判断成本：“训练一个模型并告诉我 loss”在语言形式上也是一个问题，但回答它需要执行训练作业。

第一版行为：


| 行为                         | 第一版范围          |
| -------------------------- | -------------- |
| 在授权资料中搜索、筛选、读取片段           | 允许，并限制读取量和查询次数 |
| 根据找到的内容比较、解释、总结和生成文字       | 允许，受模型调用额度限制   |
| 查找过去某次训练记录中的 loss          | 允许，保留运行记录来源    |
| 解释怎样训练模型、生成一段示例代码          | 允许作为文字回答       |
| 执行任意 Python、Shell 或用户提交的代码 | 不提供这类工具        |
| 启动训练、仿真、后台作业或继续委托其他 agent  | 第一版不提供这类执行能力   |


**资源限制仍然需要在服务端执行，不能只写进提示词。** 我建议同时约束模型总消耗、工具调用次数、读取量、请求执行时间和成员累计额度。工具本身也必须限制输入规模和执行时间，否则一次工具调用仍然可能触发大量工作。MCP 官方也明确指出，`readOnlyHint` 只是工具行为的说明，不能替代实际权限控制。可以先接入求助和资料提交功能。

## 场景

**科研最适合首先验证“找到别人已经积累的判断依据”。** Zotero 已经支持个人库与群组库分离、群组访问权限，以及可搜索的笔记。这说明文献共享本身已经有成熟做法，你的产品更值得验证的是：成员的阅读和实验经历，能否在别人需要时被有效找到

一个适合你亲自参与的场景是：你正在选择研究方法，另一位成员读过相关论文，或者尝试过类似实验。

- **已有输入：** 各自的论文批注、阅读笔记、实验配置、失败记录。
- **具体问题：** “你之前看过的研究中，哪项实验排除了这个替代解释？你当时为什么认可或质疑它？”或者“你上次复现时，遇到过哪些论文没有写清楚的设置？”
- **有用的结果：** 对方 agent 找到具体记录，说明背景和来源，帮助你调整实验设计或决定下一篇精读什么。
- **验证办法：** 选一个你当前确实在考虑的问题，用少量现成记录完成几次求助，记录哪些不确定性因此得到解决，并请资料所有者核对回答。

这里尤其要区分“论文报告了什么”“成员认为是什么”和“成员实际运行过什么”。如果回答只是重新概括公开论文摘要，这个场景还没有证明跨成员协作的价值。

**朋友家人的兴趣群组适合验证“个人实践经验能否被重复使用”。** 我更推荐做饭、出游这类有具体经历和后续行动的场景。Paprika 支持在食谱中保存个人笔记并分享食谱；AllTrails 提供朋友、家人共同维护路线清单的功能。这些是已有的信息记录与协作方式。

一个容易参与的例子是，你准备做一道亲友以前做过的菜：

- **已有输入：** 原食谱、实际调整记录、照片说明，以及愿意分享的聊天片段。
- **具体问题：** “你上次用的是哪个版本？糖量改了多少？第一次失败后调整了什么？”
- **有用的结果：** 得到亲友实际采用过的修改及其原因，帮助你决定这次如何制作。
- **验证办法：** 从一次真实的做饭计划开始，观察提供者是否省去了重新翻找和解释的工作，以及你是否实际采用了找到的经验。

出游也可以采用同样的方式，例如查询朋友某次出行的交通衔接、实际用时和住宿体验，并保留经历发生的日期。**这个方向最大的现实限制，是经验可能没有留下记录。** 如果需要家人先花大量时间录入资料，才能让 agent 回答，那么录入成本必须计入验证，不能把它当作免费前提。

**两三人的创业或开源项目适合验证“恢复一个决定背后的事实与理由”。** 用户研究实践强调从原始观察形成发现和行动；架构决策记录则保存背景、决定及其后果。这两种资料都适合回答“当时为什么这样做”

这个方向不需要限定为代码工作：

- **创业场景：** “我们为什么暂时没有做功能 X？哪次用户访谈提供了这个依据？”
- **开源场景：** “之前为什么没有采用方案 Y？当时的约束现在还存在吗？”
- **已有输入：** 不同成员的访谈笔记、讨论记录、旧方案、调试记录。
- **验证办法：** 选择一项现在需要重新判断的小决定，让 agent 找到原始依据，由当时的参与者核对，再观察这些信息是否影响当前选择。

这里的价值来自参与经历不同：一人参加过访谈，另一人处理过部署问题，彼此知道的事情自然不同。即使只有两三个人，也有验证条件。
