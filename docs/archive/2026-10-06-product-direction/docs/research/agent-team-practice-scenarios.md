# Agent 团队的实践场景研究

研究日期：2026-09-28。

## 结论与证据范围

最值得首先验证的行为是：从其他成员已有的记录中，获得能影响自己当前决定的事实、经验或理由。科研、朋友家人的兴趣交流、小型项目协作都存在这种行为，因此产品的基础设计不必绑定某一种专业任务。

本次查阅六个一手来源，确认现有工具支持哪些资料共享方式，以及实践指南怎样组织经验与决策依据。它们没有证明用户需要 agent 代为求助，也没有证明 agent 比聊天、共享文件夹或全文搜索更有效。下文的产品场景和实验均为待验证假设，没有进行真实用户实验或运行产品。没有读取现有产品草稿，没有访问用户的外部账户或向其他人发送消息。

建议先用科研或一个已有的小项目完成第一轮测试，再用家庭兴趣场景检查同一套求助机制能否复用。首先验证可追溯的信息获取与人工成本，避免同时实现三个垂直行业产品。

## 场景一：科研中的方法选择与经验核查

**建议提问：**“你之前读过或复现过的研究中，哪一项真正排除了某个替代解释？你当时为什么接受或质疑它？”例如研究多 agent 协作时，可以询问某项收益是否仍出现在单 agent 对照下，而不是泛问“推荐几篇多 agent 论文”。

真实输入可以是成员各自已有的论文注释、阅读笔记、实验配置和失败记录。不同成员的独有贡献是读过不同文献、注意过不同限制，或实际遇到过实现问题；仅仅持有相同 PDF 并不能证明成员协作的价值。Zotero 的共享库和群组注释已经提供资料协作能力，因此它们是需要比较的现有方式，而不是新需求已经成立的证明。

**低成本实验：**在一项本人正在考虑的研究问题中，选取两名成员各自已经有的 5—10 条记录，每人写两句资料范围介绍。提出 3—5 个问题，先使用自己现有资料回答，再定向询问另一人的资料。最终由本人写一页方法选择说明，明确哪些判断因对方提供的证据发生变化。不要求进行新实验或训练模型。

**已有替代方式：**直接问同学、共同读论文、搜索共享 Zotero 库或文件夹。比较双方实际投入的查找、解释和核对时间，而不能只比较答案出现的速度。

**成功证据：**回答定位到具体记录，保留“论文主张／成员评论／实际运行结果”的区别；至少一个事先存在的不确定性因此得到解决。**失败证据：**回答只重述论文摘要、编造成员跑过的实验，或核查回答比直接看笔记更费时。

## 场景二：朋友家人兴趣组的个人实践经验

**优先选择做饭或已经发生的出游经验。** 建议提问是“你上次做这道菜，用的是哪个版本，实际调整了什么？”或者“你去年走过的两条路线，实际交通和用时记录是什么？”资料来源应当是已有食谱笔记、照片文字说明、行程记录或愿意分享的聊天片段。AllTrails 和 Paprika 说明这些内容有现成保存与协作方式；产品仍须验证从零散个人记录中回答具体问题是否更方便。

**个人经验必须有公开搜索无法代替的内容。** 烹饪场景可以是某台烤箱的实际温度调整、一次失败后的配比变化；旅行场景可以是某次实际交通衔接和同行者体验。历史旅行记录需要标明日期，不能当作今天的开放情况或交通保证。园艺也适用同一结构，但本轮没有单独查找园艺的一手来源。

**低成本实验：**选择本人近期确实打算制作的一道菜或一次计划中的出游，只使用自己已经获得分享授权的记录，提出 3 个具体问题。由另一成员核对答案是否忠实于自己的经历，再观察答案是否改变配方选择或行程安排。不要为了测试强迫家人先录入大量资料；如果信息一直没有留下记录，应该把资料缺失算作产品条件不成立。

**已有替代方式：**在聊天中直接询问、转发食谱、共同编辑清单、搜索收藏。**成功证据：**找到与当前条件相关的个人调整，提供者不必再次翻找和重新解释。**失败证据：**输出通用攻略、把收藏当成亲身经历，或整理记录的成本超过本次求助节省的时间。

## 场景三：两三人项目中的用户依据与历史决定

**优先选择一个正在发生的小决定。** 创业项目可以询问“我们为什么暂时没有做功能 X，具体是哪次用户观察支持这个选择？”开源项目可以询问“之前为什么放弃方案 Y，当时的约束今天还存在吗？”真实输入可以是不同成员持有的访谈笔记、议题评论、旧方案记录或调试记录。

不同成员的独有贡献来自参与经历不同。例如一位成员参加访谈，另一位成员解决过部署问题，第三位成员维护当前实现。GOV.UK 的研究分析指南和 Nygard 的决策记录方法说明如何保留这些依据；它们没有证明两三人的团队必然需要 agent。

**低成本实验：**从本人参与过的一个小项目中，选择一项需要重新判断的决定，准备 5—10 份已有资料。要求回答列出原始约束、原始证据、之后发生的变化以及仍未知的部分。由原参与者核对，再判断现在应该维持还是调整该决定。本人可以先使用已经获准保留的历史资料进行演练，无需现在联系团队或访问外部账户。

**已有替代方式：**搜索项目议题与聊天、阅读决策记录、直接询问参与者。**成功证据：**找到自己原来不知道的重要约束，并能追溯至原始记录。**失败证据：**把现有实现当作历史理由，无法区分旧决定与新推断，或共享文档本来已经能一次搜索得到同样结果。

## 三个场景共同的最小验证方法

跨领域复用应该通过相同的求助过程验证：描述当前问题，根据介绍选择成员，在获准资料中寻找依据，返回有来源的回答，由请求方决定如何使用。首轮可以人工转交消息，不需要先实现留言板、常驻 agent 或共享空间维护器。

1. 每个参与者选择一小份已经存在的资料，并声明可以分享的范围，不预先针对测试问题重写资料。
2. 选取当前真正需要回答的问题，保留使用自己资料时的答案或未解决之处。
3. 根据成员介绍定向提问，记录人工查找与解释时间、等待时间、调用成本和引用来源。
4. 请资料所有者核对忠实性，请请求方记录回答是否改变了判断或下一步行动。
5. 同时记录直接询问、共享搜索等替代方式的成本；累计数次实际使用后再判断是否值得长期接入。

用户独自把自己过去的不同项目资料分给多个 agent，可以检查发现资料、检索和引用流程是否工作。这个实验不能证明不同人愿意分享、授权负担可接受、成员介绍能长期更新，也不能证明真实团队节约了时间。要验证这些主张，后续仍需要另一名自愿参与者，但本次研究不联系任何人。

## 架构与执行范围：设计推断

以下内容是本轮架构分析的建议，没有实现或实测。成员具有稳定身份和请求收件箱，常驻专用 agent 与在线时的工作 agent 作为两种响应执行端，使用同一请求和结果接口，共用成员额度。单次请求只交给一个执行端处理；系统不控制工作 agent 的启动和停止。常驻服务保持可接收请求，不意味着持续调用模型。

混合架构的主要成本是资料可达性和同步。云端常驻服务无法直接读取已经离线的个人电脑，需要获准的在线数据源或副本；仅存于本地的内容只能等待本地上线。成员介绍应当区分可立即提供和需要等待的资料，不能假设所有资料随时可用。

首版可以采用受限问答：允许搜索和读取授权资料以及模型内推理生成，不提供 shell、任意代码执行、训练作业、后台作业或递归委托。工具层限制读取量、返回条数和时间，服务端限制模型总预算、调用次数、请求期限和累计额度。限制输出为 1,000 token 不能限制外部训练作业；需要直接限制可用执行能力。

协议参考只用于核对现有能力，不代表已决定采用具体框架：[A2A 发现机制](https://a2a-protocol.org/latest/topics/agent-discovery/)描述能力介绍与端点，但不统一目录 API；[A2A 任务生命周期](https://a2a-protocol.org/latest/topics/life-of-a-task/)涵盖即时回复、异步任务和等待输入等状态。[MCP 工具注解说明](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)明确只读注解属于提示，不能替代权限执行。[Anthropic 的 agent 工程文章](https://www.anthropic.com/engineering/building-effective-agents)建议从简单、可组合的方法开始。
